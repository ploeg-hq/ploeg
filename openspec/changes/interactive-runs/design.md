## Context

Observed on 2026-10-13 at `703d1b7`:

- **Harness seam.** `Adapter.Run(ctx, spec, env) (OutcomeReport, error)` (`pkg/harness/adapter.go:36-40`). `RunEnv` (`:43-68`) carries outputs (Checkpoint callback, transcript recorder, remote session) and no input. Cancellation of `ctx` means the Lease is lost (`:26-27`).
- **ACP adapter.** One `session/prompt` turn per Run (`pkg/harness/adapters/acp/acp.go:244-258`), with an idle watchdog and a prompt wall (`awaitPrompt`, `acp.go:324-374`) and a `session/cancel` when the turn ends any other way (`acp.go:279-293`). In this design "turn" always means an ACP prompt turn, never a Round. `RequestPermission` decides at once from the mode (`client.go:65-103`); its doc says "there is no human in a worker pod". Elicitation, `fs/*` and `terminal/*` are not implemented, and the comment places interactivity "above Ploeg (backlog #101), never inside a one-shot pod" (`client.go:17-37`). The adapter says client methods "must never do HTTP, disk I/O or a blocking send" (`client.go:39-42`). In the pinned SDK (`acp-go-sdk` v0.13.5, `connection.go:395-421`) each inbound **request** is handled on its own goroutine and only **notifications** are processed in sequence. So a `RequestPermission` handler can wait on a channel without stopping the read loop, provided it never does HTTP itself and honours its context. That comment is accurate for `SessionUpdate`, not for requests.
- **Streaming.** At most 15 Checkpoints plus a 5-minute heartbeat (`acp.go:397-402`). ADR-0090's transcript (proposed, implemented) ships typed entries every 2 s and serves them by polling `GET /api/v1/operator/runs/{id}/transcript`.
- **Steering today.** A person's note reaches the next Run's briefing at claim (`operator_notes`, migration `0048_operator_notes.sql`; `ConsumeOperatorNotes` in `pkg/store/operator_notes.go:131`), and ADR-0068 (accepted) rejected putting context items into a running Run between turns.
- **Liveness.** Every running Run has its own renewed deadline (`agent_runs.expires_at`, swept by `ExpireRuns`, `pkg/store/shift.go:548`); only a writing Run also holds the Shift's Lease (glossary, ADR-0010).
- **Existing interaction vocabulary.** Operator Executions already have `pause`, `resume`, `message`, `waiting_input`, `take-control` and `handback` (`pkg/store/operator_execution.go:218-276`), but their Executor is the consumer: ploegd only records state the consumer reports. Unfold ADR-0023 retires that path.
- **Worker network.** The worker reaches the model gateway, the forge and ploegd only; every control channel must be pulled (Unfold ADR-0023's drivers; `docs/contracts/worker-control.md`).

ADRs: 0006 (accepted: AHP parked; "an interactive surface belongs in a separate service", R6), 0010 (accepted: a Lease is write access only), 0068 (accepted: context reaches the next Run), 0090 (proposed: transcript, redaction, polling), 0024 (proposed), 0034, 0044 (accepted: requeue from a chosen Round), 0075 (proposed: a stopped writing Run leaves a checkpoint), 0012/0048 (Holds), 0069, and 0102 (proposed, `submit-work-items`: the submission route). Rules: R2, R3, R4, R5, R6, R13, R14, R15.

## Goals / Non-Goals

**Goals:**
- A person answers permission requests and questions, sends messages, pauses and resumes an attended Run that `ploeg-worker` executes.
- No interaction can hang a Run, keep a Run or its Lease alive after its pod died, or turn a pause into an automatic retry.

**Non-Goals:** see the proposal; in particular no UI, no AHP, no cross-pod session resume.

## Decisions

1. **The relay runs through ploegd, pulled by the worker.** The worker posts a request (`POST /api/v1/runs/{token}/interactions`) immediately, not in transcript batches, and long-polls `GET /api/v1/runs/{token}/inbox?after=<seq>&wait=<≤25s>` for answers, messages, pause, resume and cancel. ploegd stores both in one table (`run_interactions`: run, sequence, kind, payload, state `open|answered|expired|withdrawn|delivered|carried_over`, actor, deadline, times). Alternatives rejected: a consumer attaching to the ACP session (needs inbound access to the sandbox, rejected by ADR-0006 and Unfold ADR-0023); piggybacking on Lease renewal (renewal cadence is too slow for a person waiting, and mixes crash-safety with interaction).
2. **Attended is a property of the Run, set at submission.** A boolean on `POST /api/v1/operator/work-items` (`submit-work-items`), stored on the Work Item and copied to each Run its Shifts create, including retries, re-opened Rounds and Runs after a requeue (ADR-0044). It is part of the submission's R13 fingerprint. Next to it, `autoApprove` (bool, default false, refused as `true` without `attended`) is stored and copied the same way and joins the fingerprint (Decision 12). `AdmitOperatorExecution` gets no such field: its Run is executed by the consumer. Unattended Runs never relay, so tracker work keeps its unattended guarantees.
3. **Deadlines fall back to today's behaviour.** Team settings `interaction.answerTimeout` (default 10 min, at most 30) and `interaction.pauseBound` (default 30 min). An expired permission resolves by the Team's configured permission mode, which is exactly what an unattended Run does; an expired question is refused, which is what the adapter does today. Alternative rejected: expire to `stuck` at once; that turns every coffee break into a needs_human.
4. **ACP first.** OpenCode and OpenHands both speak ACP (`docs/contracts/acp-profiles.md`), so one adapter covers the Harnesses a consumer is most likely to offer. `RunEnv` gains an optional `Interaction` port (request, inbox channel, acknowledge, confirm pause); a nil port is today's behaviour. The ACP adapter adds the `ask` mode (used when `autoApprove` is false), an elicitation handler for attended Runs, a turn loop that sends queued messages as further `session/prompt` turns, and pause by `session/cancel`. Other adapters keep a nil port and degrade as specified.
5. **The worker owns the network, the adapter owns the protocol.** A worker goroutine does the HTTP and feeds a channel; the adapter's handlers only wait on that channel with their request context, never on the network, which keeps the read-loop rule.
6. **Clocks.** While a request is open or the Run is paused, the ACP idle watchdog and prompt wall stop; they measure the agent, not a person. `PLOEG_HARNESS_TIMEOUT` and the Job's `activeDeadlineSeconds` keep counting, so a Run waiting on a person still ends. The worker keeps renewing the Run, and a writing Run's Lease, as usual (R2). Deadlines and the pause bound are stored timestamps, so a ploegd restart neither resets nor skips them.
7. **Budget while waiting.** The Run's Inference Account keeps its Hold (R15, ADR-0048); a waiting agent makes no model calls, so spend does not grow, but compute time does. The pause bound and the harness timeout cap it.
8. **Streaming stays the transcript.** Interaction requests and resolutions are also written as transcript `stage` entries, so a consumer following the transcript sees them in order; no change to the transcript contract. Checkpoint limits stay.
9. **Recovery.** Interactions belong to one Run. When the Run expires or ends, the sweeper marks open requests `expired` and unacknowledged messages `carried_over`, and writes each carried-over message as an operator note so the next Run's briefing has it (the `operator_notes` path; ADR-0068's "context added while a Shift runs reaches the next Run"). A Run with a pause in effect that expires is closed without retry and its Work Item goes to `needs_human` with `paused_run_lost` (R3, R14).
10. **Ending a pause.** When the pause bound passes, ploegd records the Run's Outcome as `stuck` with `paused_too_long` (R4), puts a stop in the inbox, and settles the Run's Hold through the existing settlement path (R15); a worker that never reads the stop is ended by Run expiry, which changes nothing already recorded. When `PLOEG_HARNESS_TIMEOUT` or the Job deadline ends a paused Run first, the Run ends the same way, with reason `paused_too_long`, and is not retried automatically (R3).

11. **Messages narrow ADR-0068 (owner decision 2026-10-13).** Keeping interactivity implies that a message reaches a running attended Run, which ADR-0068 (accepted) rejected. The ledger replaces a record only whole (`supersedes:` marks the old row superseded), and 0068 stays right for context items and for every unattended Run, so a new record narrows it with `supersedes: none`, the way ADR-0080 narrowed five records: ADR-0104 (proposed). It is a separate record rather than a `supersedes` on ADR-0100 because 0100 replaces nothing, and a full supersession would mark 0068 replaced for tracker work too. A message to an attended Run whose Harness supports interaction reaches it at the next prompt turn; an attended Run's recorded inputs are its claim plus its interaction log; context items, and messages to unattended or non-interactive Runs, reach the next Run as 0068 says. On accepting 0104, a dated note is appended to 0068's More Information.
12. **`autoApprove` (owner decision 2026-10-13).** "Approve tool use automatically" is a per-Run flag. `true`: the adapter decides every permission request at once by the Team's permission mode, as an unattended Run does, and relays none; questions, messages, pause and resume still reach the person. `false`: every permission request is relayed with its options, and when its deadline passes the Team's permission mode decides (Decision 3). In both cases a Team mode of `deny_all` still refuses without relaying, because a person cannot widen what the Team forbids, and the storm caps apply. The flag is stored on the Work Item and each Run, is part of the fingerprint, and is kept on retries, re-opened Rounds and requeues. Unattended Runs ignore it.

Durable commitments are in ADR-0100 (relay, fallback and `autoApprove`), ADR-0101 (pause) and ADR-0104 (messages narrow ADR-0068).

## Risks / Trade-offs

- [Pods stay alive while people think, costing compute and a cluster slot] → answer timeout and pause bound; attended Runs count against `maxRunning` like any Run.
- [A person approves a dangerous tool call] → the Team's mode is still the ceiling: under `deny_all` nothing is relayed, and `ask` exists only for attended Runs without `autoApprove`.
- [With `autoApprove: false` every read is relayed, so a busy agent asks often] → the person can switch to `autoApprove: true` for the next session; the answer timeout bounds each wait; the storm caps still cancel a runaway session.
- [Request payloads carry secrets from tool input] → ADR-0090's redaction on both sides, 4 KiB bound per request.
- [ACP elicitation is unstable in the protocol (`acp-go-sdk` exposes it as `Unstable…`)] → behind the attended flag, and its wire may change; the conformance suite covers it per profile.
- [Long-poll load on ploegd] → one connection per attended Run, 25 s holds; measured before adding SSE.

## Migration Plan

1. Store and Run API routes, behind `PLOEG_RUN_INTERACTION=off` by default.
2. Worker and ACP adapter; a worker that does not know the routes simply never relays.
3. Operator API reads and commands; then the attended flag on `POST /api/v1/operator/work-items`, once `submit-work-items` has shipped. Rollback: switch off; open requests expire to today's behaviour.

## Open Questions

1. **ADR-0006 says an interactive surface belongs in a separate service, and `client.go:35-37` says interactivity never belongs inside the pod.** This design keeps the surface in the consumer and adds a relay inside Ploeg. One of 0006's own re-evaluation triggers ("an interactive 'attach to a running agent' requirement becomes real") fired with the owner's decision of 2026-10-13. Recommendation: keep ADR-0006 in force (its decision is about AHP) and record the relay in ADR-0100, which names 0006; decide at 0006's 2026-10-31 review whether its consequence text needs a superseding record. Trade-off: leaving 0006 untouched keeps a sentence that reads against this change; superseding it reopens the AHP verdict, which nothing here requires.
2. **Unfold ADR-0023 (accepted) says no pause in v1 and that interactive permission answers go away.** Recommendation: the Unfold side amends its record; Ploeg builds the relay because the owner's 2026-10-13 decision overrides. Trade-off: until Unfold's record changes, the two repositories document opposite intents.
3. **Should an attended Run stay open after its turn ends, waiting for a follow-up message?** Recommendation: a per-Team `interaction.linger`, default 0 (finish as today), at most 15 min. Trade-off: chat-like sessions need it; every minute of linger is an idle pod and a held Lease.
4. **What does an expired permission do: the Team's mode, or always reject?** Resolved 2026-10-13 with Open Question 9: the Team's mode decides when the deadline passes. Recommendation was: the Team's mode, so attended is never less capable than unattended. Trade-off: a person who walked away has effectively approved what the Team's mode allows; always-reject is safer and makes more Runs end stuck.
5. **Should the per-Run model key be blocked while paused?** Recommendation: no in v1; the agent is idle after a confirmed cancel. Trade-off: blocking enforces "no spend while paused" (R15-style), but ploegd has no unblock path for a key today, so resume would need a new key and a new account.
6. **Missing domain terms.** The glossary has no term for an interaction request, an attended Run or a pause of a Run (only Operator Execution pause exists). Recommendation: add "Interaction" and "Attended Run" to `docs/domain/model.yaml` and regenerate with `mise run domain` before implementation. R14 already lists Run under "Also applies to", so its pause clause needs no extension. Trade-off: none beyond the edit; without it, three changes would invent wording.
7. **Run-level commands or Operator Execution commands?** Recommendation: Run-level routes with the Operator Execution's action names and R13 semantics, because Unfold ADR-0023 retires Operator Executions. Trade-off: two vocabularies coexist until Operator Executions are removed.
8. **ADR-0068 (accepted) rejected putting context into a running Run between turns.** Resolved 2026-10-13: the owner's decision to keep interactivity implies messages reach a running attended Run. A new proposed record, ADR-0104, narrows 0068 for messages to attended Runs whose Harness supports interaction (Decision 11); context items and unattended Runs keep 0068's behaviour. Superseding 0068 whole was rejected because it would make every context item, on every Run, eligible for mid-Run delivery.
9. **What does "Approve tool use automatically" mean?** Resolved 2026-10-13: a per-Run `autoApprove` flag (Decision 12). True decides permissions by the Team's permission mode without relaying; false relays every permission request and lets the Team's mode decide at the deadline. Questions, messages and pause reach the person either way.
