## Goals / Non-Goals

**Goals:**
- An Operator Consumer admits a manual-origin Work Item and `ploeg-worker` executes it through ordinary Shift dispatch.
- A lost response, a ploegd restart or a vanished consumer never duplicates, loses or re-queues paid work.
- The consumer follows and steers the work with the routes that already exist.
- `select-harness-per-run` and `interactive-runs` gain the Admission they depend on, without this change defining their fields.

**Non-Goals:** pause, mid-Run messages, push events, Harness and model choice, auto-approval, tracker binding, priority, deleting Operator Executions (proposal, Non-goals).

## Decisions

1. **A new route and store function, not a variant of an existing one.** `POST /api/v1/operator/work-items` sits beside the existing `GET` on the same collection (`operator.go:180`) and is registered from its own file, like `registerOperatorAsk`. Its handler reuses `executionActor`, `decodeExecution` (128 KiB, unknown fields refused) and `operatorAuditActor`. Its store function `AdmitOperatorWorkItem` runs one transaction. Rejected: extending `AdmitOperatorExecution` with a "worker executes" flag, which keeps placeholder semantics on the path that is being retired; and `IngestAssigned`, for the re-queue on conflict above.
2. **The request.** `requestId`, `team`, `target` (registered key), `title` (1–200), `description` (1 to 110000, the Operator Execution objective's upper bound), optional `budgetUsd`, plus the optional fields other changes define: `harness` and `model` (`select-harness-per-run`, ADR-0098 and ADR-0103) and `attended` and `autoApprove` (`interactive-runs`, ADR-0100). Unknown fields are refused, so those changes add their fields to the schema and the Go type when they land. The response is `{schemaVersion, workItem: {id, team, state, shiftId}, created, replayed}`; `select-harness-per-run` adds the resolved Harness and model per Role. The schema lives in `docs/contracts/operator-api.v1.schema.json`.
3. **Identity and idempotency.** A new table `operator_work_admissions(consumer, request_id, actor, fingerprint, work_item_id, created_at, PRIMARY KEY (consumer, request_id))` in the next migration. The transaction takes `pg_advisory_xact_lock` on `consumer:requestId` as `AdmitOperatorExecution` does (`operator_execution.go:99-101`), reads the row, and on a hit compares fingerprint and actor (replay or 409 `request_conflict`) without touching the Work Item. On a miss it inserts the Work Item with `provider = 'manual'`, `external_id = <consumer>:<requestId>`, `origin = 'operator'`, `operator_owned = false`, state `queued`, the resolved target columns and `route_rule = 'operator-admission'`, then the admission row, then the audit event. `provider = 'manual'` keeps ADR-0069 (Unfold's design proposes `'unfold'`; Ploeg does not name its consumers). Because Operator Executions use the same `manual` provider and `<consumer>:<session>` key (`operator_execution.go:130-133`), an insert that hits `(provider, external_id)` answers 409 `request_conflict` rather than adopting the operator-owned row. The fingerprint is `executionFingerprint` (`operator_execution.go:74-78`) over the decoded request without `requestId`.
4. **Budget.** `budget_usd` on the Work Item is set to `budgetUsd` or, when absent, the consumer's `maxBudgetUsd`. `OpenShift` then caps the pool (`shift.go:62-64`), which also bounds a synthesized unmetered pool. Requeue already re-checks its pool against the requeuing consumer's limit. Rejected: refusing when the plan's pool exceeds `maxBudgetUsd` (what requeue does), because every Admission to a Team with a pool above 25 would then need an explicit budget; see Open Question 2.
5. **Dispatch.** After commit, the handler calls `Engine.EnsureShift`; an error is logged and repaired by the sweeper, as on the webhook path (`server.go:306-310`). Before the transaction, the handler asks the engine whether the Team is dispatchable by a Shift. That needs one new method on `httpapi.ShiftEngine` (for example `Dispatches(team) bool` over `planFor`). Rejected: admitting into the legacy plan-less queue (`nextClaimableQuery`), where the allotment never becomes a Shift pool and the ceiling would not hold.
6. **Events.** The Admission writes `operator.work_item.admitted` with `{request_id, team}` under the actor `operator:<consumer>:<actor>`; the existing feed serves it after `operatorEventJSON` allowlists `requestId`. No new read route: Unfold ADR-0023 chose polling, and an SSE endpoint waits for a measurement.
7. **Commands stay where they are.** Withdraw, requeue and notes work on the admitted item because it is not operator-owned. No `/commands` route is added: Unfold ADR-0023 names `message` as the only new command, and `/notes` already is that command with `commandId` idempotency and an `expectedShiftId` guard. Pause, resume and messages to a running Run are per attended Run in `interactive-runs`.
8. **Claim and scaler predicates do not change.** Admitted Runs are ordinary `pending` Runs of a planned Role, counted by the Role's scaler query (`scaledjob.yaml:75`) and claimed by `ClaimRoleWithin`; `TestClaimRoleAgreesWithPendingRuns` stays as is. The `operator_owned` and `operator_executions` predicates, including `scaledjob.yaml:79`, are removed only by the retirement change.

## Risks / Trade-offs

- [Two Admission paths share the `manual` provider and the `<consumer>:<id>` key space] → the 409 on collision in Decision 3 and a store test that admits both with the same identifier.
- [Admitted work now counts against `maxRunning` and competes in the Team Queue with tracker work] → intended: one dispatch; the Team's cap and KEDA ceilings bound it (`docs/architecture.md` §3).
- [A Team's plan pool silently shrinks to the consumer's ceiling] → the response and the `round.opened` event carry the Shift pool; Open Question 2.
- [Infrastructure retries spend again without a person asking] → bounded by R5 and ADR-0021 counters and visible in the event feed; Open Question 3.
- [Events are snapshot-consistent, not a lossless change feed] → the consumer re-reads `GET /operator/work-items/{id}` when it needs the current state, as the contract already says.
- [Events are team-scoped, not consumer- or person-scoped] → a consumer filters by the people it serves; R6 keeps person records in the consumer.

## Migration Plan

1. Land the migration, the store function and the route with the contract schema. Nothing calls it yet; Operator Executions are unchanged.
2. Consumers move to the route under their own records (Unfold ADR-0023 increments 2–9).
3. The retirement change refuses new Operator Executions, waits until no open row remains, then removes the exclusions and the tables in a new migration and the legacy scaler clause.

Rollback: unregister the route. Admitted Work Items stay ordinary queued or settled Work Items and keep dispatching.

## Open Questions

1. **Retire Operator Executions in this change or a later one?** Recommendation: a later change, `retire-operator-executions`, once Unfold has moved. Trade-off: two changes and a period with both paths, against touching ten scheduler predicates, the scaler query and a destructive migration in the same change that adds a route; the retirement is unsafe until consumers have moved anyway.
2. **No `budgetUsd` and a plan pool above `maxBudgetUsd`: cap or refuse?** Recommendation: cap at `maxBudgetUsd` and report the pool in the response. Trade-off: a silent cap can starve a large plan's later Rounds; refusing (as requeue does) is explicit but makes every Admission to a large Team name a budget.
3. **Should infrastructure failures of admitted work be retried automatically?** Recommendation: yes, under R5 and ADR-0021 exactly as tracker work, since the Work Item is ordinary. Trade-off: a retry spends without a person asking, which Unfold's rule "a restart never silently repeats paid work" could be read to forbid; the alternative is an operator-owned lifecycle, the thing this change removes.
4. **May a withdrawn admitted Work Item be requeued?** Today requeue refuses `withdrawn` (`pkg/store/requeue.go:37`), and a tracker item comes back by reassignment, which a manual-origin item cannot. Recommendation: keep it final; the consumer admits a new Work Item with a new `requestId`. Trade-off: the new Work Item loses the first one's notes and Shift history; allowing it means widening `operatorRestartStates` for manual origin only.
5. **Does ADR-0102 supersede ADR-0024 now, while both are proposed?** `go test ./internal/ledger/` derives "superseded by 0102" for 0024's Records row from `supersedes: 0024`, so the index shows 0024 as superseded before 0102 is ratified. Recommendation: keep `supersedes: 0024` (the owner chose on 2026-10-13 that Ploeg executes every session) and ratify both together. Trade-off: if 0102 is rejected, its `supersedes` must be set to `none` and the 0024 row restored.
6. **Domain language to update before implementation (not edited here).** The glossary defines Operator Consumer as requesting "an Operator Execution", and Work Item as coming "from an Operator Execution admitted for an Operator Consumer"; R2, R5, R13, R14, R16 and R18 are worded for Operator Executions. There is no term for an operator-admitted manual-origin Work Item. Recommendation: in `docs/domain/model.yaml`, let Admission cover "a manual-origin Work Item admitted for an Operator Consumer", reword Operator Consumer and Work Item accordingly, mark Operator Execution as being retired, and add a rule that a replayed Admission never re-queues work. Trade-off: none beyond the edit; without it the specs use terms the glossary still ties to the retiring path.
7. **Should the Admission accept a Round to start from or a plan override?** Recommendation: no; the Team's plan decides, as for tracker work. Trade-off: a consumer cannot run "review only" sessions without a Team configured for them.
