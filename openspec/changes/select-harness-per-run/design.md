## Context

Observed on 2026-10-13 at `703d1b7`:

- **One Harness per pod.** `ploeg-worker` builds one adapter from `PLOEG_HARNESS*` before it claims (`cmd/ploeg-worker/main.go:146-161,188-192`), so a misconfigured Team fails at startup, not after taking a Lease (`pkg/worker/adapters.go:116-119`). The chart resolves the Harness role → team → global (`ops/helm/ploeg/templates/_helpers.tpl:181-184`), and per workload also decides DinD (`:210-211`), credential isolation from a list of isolation-qualified Harnesses (`:133-165,226`: `openhands`, `acp/openhands`, `exec`) and the agent image (`:185-188`).
- **Claim and scale signal.** A planned Role's scaler query is `team = … AND role = … AND state = 'pending'` (`ops/helm/ploeg/templates/scaledjob.yaml:64-75`), byte-identical to `ClaimRoleWithin` and `PendingRuns` (`pkg/store/shift.go:342,516`). The open change `reserve-runs-for-launchers` (ADR-0072, proposed) replaces the SQL with a demand endpoint computed by `PendingRuns`.
- **Admission.** `AdmitOperatorExecution` (`pkg/store/operator_execution.go:41-53,92-163`) creates a Work Item, Shift and a `running` Run with role `operator` that no worker claims; the consumer executes it (`docs/architecture.md` §2-3, ADR-0024 proposed). Unfold ADR-0023 (Unfold repository, `apps/unfold/docs/adrs/0023-unfold-submits-work-to-ploeg-and-never-executes-it.md`, accepted 2026-10-11, not implemented) retires that path in favour of `POST /api/v1/operator/work-items`, which creates a Work Item that is not operator-owned and opens its Shift with the Team plan. Ploeg registers no such route today (`pkg/httpapi/operator.go:177-201`); the `submit-work-items` change (ADR-0102, proposed) plans it.
- **Model.** The chart renders each (Team, Role) inference policy with exactly one model (`ops/helm/ploeg/templates/_worker_control.tpl:21`, `models: [role.model | team.model]`), and `LLM_MODEL` in the worker pod is the same value (`_helpers.tpl:415-416`). The Unfold plan for the New-session dialog proposes letting a person also choose a model per session from the models the Team lists; this plan's earlier answer was no (ADR-0039). The owner decided on 2026-10-13 to allow it (Open Question 6, resolved; Decision 7).
- **Qualification.** `docs/contracts/acp-profiles.md` says `qwen-code` and `goose` are not qualified by a live Run; the `opencode` profile's provider keys are unverified (backlog #64); the `openhands` ACP profile is checked against a stub and isolation-qualified.

Accepted ADRs designed within: 0012 (budgets authorized per Run from the Shift pool), 0034 (placeholders in the Harness, credentials in the worker), 0037 (airgapped default), 0069, 0084 (claude-environment paid by the Team's plan). Proposed records taken into account: 0019 (a failed writing Run re-opens its Round), 0024, 0039, 0071 (state in PostgreSQL, ploegd is not a Kubernetes operator), 0072, 0091, 0097, 0102 from `submit-work-items`, and 0103 (this change), which narrows 0039 and 0091.

## Goals / Non-Goals

**Goals:**
- A person picks a Harness per session; ploegd enforces the Team's allowlist and qualification.
- Every Run of that session runs the Harness it was given, including retries, and no Run waits for a Harness no workload can run.

**Non-Goals:** tracker-originated selection, selection for Teams without a plan, building images, interaction. A model outside the Role's policy.

## Decisions

1. **The choice lives on the Run, resolved when the Run is created.** A new nullable column `agent_runs.harness_requested` (the qualification key, `acp/opencode` style, matching `_helpers.tpl:137-143`) is filled when the Shift inserts a pending Run (`OpenRound` and `ReopenRound`, `pkg/store/shift.go:130,295`), from the submission's request stored on the Work Item. Storing it on the Run, not resolving at claim, keeps the claim predicate a plain column comparison that the scaler can copy. Alternative rejected: resolve at claim from the Work Item, which needs a join in the scaler query and a Role default the scaler cannot see.
2. **Allowlist and default in the chart, read by ploegd.** `executor.teams[].harnesses` lists allowed Harness entries, each with the same fields as today's `harness` block (image, ACP profile and settings, DinD, isolation), plus `default`; a Role's `harnesses` narrows it. `PLOEG_TEAM_HARNESSES` (from `record-harness-per-run`) gains `allowed` and `qualification` per Role. A Team without `harnesses` keeps its single `harness` block, which becomes a one-entry allowlist.
3. **One workload per (Team, Role, Harness).** The chart renders a ScaledJob (or CronJob) per allowed Harness, each a single-purpose pod exactly as today. Its scaler query adds `AND (harness_requested IS NULL OR harness_requested = '<key>')`; `ClaimRoleWithin` and `PendingRuns` add the same clause when the claim names a Harness, with the key derived from the claim's `harness` and `harnessProfile` exactly as `ploeg.qualificationHarnessName` derives it (an empty `acp` profile is `opencode`), and a new partial index `(team, role, harness_requested, id) WHERE state = 'pending'` serves it. A Run with no stored Harness is claimable by every workload of its Role, which is today's behaviour. A Team without a plan keeps its single workload: its scaler counts queued `work_items` (`scaledjob.yaml:79`), and its role-less claim tries a synthesized Shift's Run before the pre-Shift claim (`pkg/httpapi/server.go:533-555`, `pkg/shiftengine/engine.go:125-134`), so there is no per-Harness signal to scale on. `TestClaimRoleAgreesWithPendingRuns` gains Harness cases. If `reserve-runs-for-launchers` lands first, its demand endpoint takes `harness=` and computes with the same predicate. The durable choice is ADR-0099.
4. **Admission refuses, never queues, what cannot run.** The admission checks the allowlist and qualification synchronously and answers a client error. Because the chart renders a workload for every allowed entry, an admitted Harness always has a workload; a Run can only be stranded by an image that lacks the binary, which `CheckHarnessBinary` turns into a crash-looping pod that alerts, not a silent stall.
5. **Qualification is a chart-owned list, shown and gated.** The chart keeps one list of qualified Harness keys next to `ploeg.isolationQualifiedHarnesses`, updated when the live conformance suite (`pkg/harness/harnesstest/live_test.go`, backlog #69) passes for that Harness. An unqualified entry other than the Role's default is admitted only when the Team sets `allowUnqualifiedHarnesses: true`; the Role's default is always admissible, because tracker work already runs it, so a Team without an allowlist behaves as today. The Teams read shows the status per entry.
6. **Budget is unchanged.** Each Run is authorized from the Shift pool by its Role's cap (ADR-0012), whatever its Harness. The cap does not depend on the model a session chooses (Decision 7): a Run's cap is its Role's. A Harness with its own payer (`claude-environment`, ADR-0084) is excluded from allowlists in this change.

7. **Model per session, from the Role's policy (owner decision 2026-10-13).** The chart renders each (Team, Role) policy with `models` (the allowed aliases, from a new `role.models` list, default `[role.model | team.model]`) and `defaultModel` (`role.model | team.model`); `PLOEG_WORKER_LLM_POLICIES` carries both. `POST /api/v1/operator/work-items` takes an optional `model`. ploegd refuses it with 422 `model_not_allowed`, naming the allowed models per Role and creating nothing, when no Role of the Team's plan lists it or when the Team's Roles have no managed inference policy (`model_requires_managed_inference`). The request's model is stored on the Work Item with the request and joins the R13 fingerprint. When the Shift inserts a pending Run (`OpenRound`, `ReopenRound`, `pkg/store/shift.go:130,295`), it fills a new nullable `agent_runs.model_selected` with the requested model when the Role's policy lists it, otherwise the Role's `defaultModel`; a Run whose Role has no policy stores none. Retries, re-opened Rounds and Runs after a requeue resolve from the same stored request, so they keep the model. `LLMControl.Reserve` scopes the account's `models` to `[model_selected]` when set, so the minted key allows only that model; `recordRunConfig` writes `configured_model` from `model_selected` (ADR-0091 as narrowed by ADR-0103), so `modelMismatch` compares against the chosen model. The claim response carries `model`; the worker uses it as `LLM_MODEL` and falls back to its environment only when the response has none. The model needs no workload of its own, so ADR-0099's predicate is unchanged. The admission response lists the resolved Harness and model per Role. The durable choice is ADR-0103, which narrows ADR-0039 point 1 and ADR-0091's model rule without superseding either.

## Risks / Trade-offs

- [Workloads multiply: Teams × Roles × Harnesses ScaledJobs, each polled by KEDA] → the allowlist is short by intent; KEDA polls are one index-only count each; ADR-0072's demand endpoint reduces it to HTTP reads.
- [Cold start per Harness, no warm pod shared across Harnesses] → accepted; warm pools are per workload today as well.
- [A Run whose stored Harness lost its workload after a values change waits forever] → Helm cannot see pending Runs, so the chart cannot refuse the removal; instead ploegd exposes pending Runs per stored Harness on the Teams read and an alert fires when a stored Harness is not in the current allowlist.
- [Isolation decisions are per Harness and stay per workload] → kept, which is the main reason for Decision 3.
- [A chosen model costs more per token than the Role's default, under the same cap] → the cap still bounds the Run; a Run that exhausts it ends as today, and cost per Role is grouped by `configured_model`.
- [An older worker ignores the claim's `model` and calls its pod's `LLM_MODEL`] → the key is scoped to the resolved model, so the gateway refuses the call and the Run fails visibly; ship workers before enabling the `model` field.

## Migration Plan

1. Ship the migration (column and partial index) and ploegd reading the allowlist; Runs store a Harness only once the chart passes an allowlist.
2. Ship the chart: one workload per allowed entry, scaler query with the Harness clause. A Team without `harnesses` renders exactly as before plus a clause that matches its single key or null.
3. Ship the policy list in the chart (a Role without `models` renders as today), `model_selected`, the scoped reservation and the claim's `model`; then workers that read it.
4. Enable the `harness` and `model` fields on `POST /api/v1/operator/work-items` once `submit-work-items` has shipped. Rollback: remove the fields from the consumer; stored values stay, remain claimable by their workloads, and keep their scoped keys.

## Open Questions

1. **Which admission carries the Harness?** Resolved in planning: the `submit-work-items` change (ADR-0102, proposed) adds `POST /api/v1/operator/work-items`, and the Harness goes on that route only. `AdmitOperatorExecution` gets no Harness field, because its Run is executed by the consumer and a field there would promise a choice no Ploeg worker honours. This change cannot ship its admission part before `submit-work-items`.
2. **Does a session's Harness apply to every Role of the plan or only to writing Roles?** Recommendation: every Role whose allowlist contains it, others use their default, and the admission response lists the resolved Harness per Role. Trade-off: a reviewer may silently run a different Harness than the person picked; restricting to writers is simpler to explain but surprises a person who wants one Harness throughout.
3. **One multi-Harness image or a workload per Harness?** Resolved 2026-10-13: the owner confirmed a workload per Harness (ADR-0099). Recommendation was: a workload per Harness. Trade-off: more ScaledJobs and cold starts, against keeping per-Harness images, DinD, isolation and fail-fast adapter construction exactly as they are. A single image with several Harnesses would need the adapter built after the claim, isolation decided per Run inside the pod, and an image Ploeg does not publish carrying every agent.
4. **May a Team admit unqualified Harnesses (`qwen-code`, `goose`)?** Recommendation: only with `allowUnqualifiedHarnesses: true` per Team, shown as unqualified on the Teams read. Trade-off: the opt-in makes trials possible; without it, a profile can only be qualified by a Team that already runs it by default.
5. **Should `claude-environment` be selectable?** Recommendation: not in this change. Trade-off: it is paid by the Team's Claude plan rather than the Shift pool (ADR-0084), so allowing it per Run changes who pays per session; a later change can add a payer-aware rule.
6. **Should a session also choose its model?** Resolved 2026-10-13: yes, from the Team's list (option (b)). The owner decided that an admission may name a model alongside the optional Harness; ploegd accepts it only when the Role's managed inference policy lists it and otherwise refuses with a clear error; absent, each Role uses its default model. It applies per Role like the Harness: Roles that do not list it use their default, and the response lists the resolved model per Role. The Run records the resolved model as ADR-0091's `configured_model`, its key is scoped to that model, and retries, re-opened Rounds and requeues keep the stored model. Implemented by Decision 7 and the `model-selection` spec; recorded in ADR-0103 (proposed), which narrows ADR-0039 and ADR-0091 without superseding them. The option not chosen, (a) keep the model the Role's, is kept in ADR-0103's considered options.
7. **Relation to ADR-0024 (proposed).** Executing operator sessions in `ploeg-worker` retires the consumer-as-Executor half of ADR-0024. Resolved in planning: ADR-0102 (`submit-work-items`) supersedes 0024. This change only needs the route to exist.
