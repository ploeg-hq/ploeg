# Tracker configuration and historical board notes

The tracker owns current work and priorities. Ploeg receives configured provider events and resolves a Work Target from the registered Scope. An operator consumer registers its own task sources and repository mapping; there is no universal project-ID default.

For current integration behavior, read [tracker execution binding](../contracts/tracker-execution.md), the [Vikunja provider](../../pkg/provider/vikunja/vikunja.go), the [ClickUp provider](../../pkg/provider/clickup/clickup.go) and the [GitHub Issues provider](../../pkg/provider/githubissues/githubissues.go). To connect GitHub Issues, follow [Connect GitHub Issues](../how-to/connect-github-issues.md); it dispatches on a `ploeg:<team>` label rather than an assignee, and ploegd does not check or register its webhooks.

To have agents implement an OpenSpec change, put a line `openspec: <change-id>` in the tracker item's description. See [OpenSpec Work Items](../contracts/README.md#openspec-work-items) for what the Run then does.

A queued Work Item waits before its first Shift while its tracker says it waits for an item that is not done ([ADR-0123](../adrs/0123-dispatch-waits-for-tracker-dependencies-and-an-opt-in-free-premise-check.md)). On Vikunja that is a "blocked by" or "follows" relation; on GitHub Issues a "blocked by" issue dependency; on ClickUp a task the item is "waiting on", done when its status is of the closed or done type. ploegd reads the relations when it would open the Shift and again every `PLOEG_DEPENDENCY_RECHECK` (default `5m`) while the item waits, and the operator API lists the open ones under the Work Item's `waitingFor`. `PLOEG_DEPENDENCY_HOLD=false` switches the hold off. A tracker that cannot be read holds nothing new.

A Team with `teams.<name>.premiseCheck.model` set gets one classifier call on that gateway model before its first writer, from the next sweep. ploegd reads the model's price from LiteLLM first and makes no call unless every deployment of it costs nothing, mints a key that reaches only that model with fallbacks disabled, and refuses a reply the gateway charged for. `proceed` opens the Shift. `ask` and `too_big` move the Work Item to `needs_human`, comment the question on the tracker task and spend nothing on a writer; assigning the task again sends it on without a second check. After three failed attempts the check is recorded as `skipped` and dispatch goes on.

A Role whose `claude-environment` Runs a client carries (chart `harness.claudeEnvironment.carrier: client`, [ADR-0112](../adrs/0112-a-claude-environment-run-uses-the-claude-login-of-the-person-it-acts-for.md)) gets no worker. Its Work Item waits as `needs_human` with `waitingForClient` (reason `start_from_claude_code`) until the person it acts for claims the Run with `POST /api/v1/operator/work-items/{id}/claim` and dispatches it with their own Claude Code. For tracker work that person is the tracker user who assigned it, mapped to Ploeg's person id in `trackers.<tracker>.people` (`{<username>: <person id>}`, compared without case). An unmapped user's work waits, naming the tracker user, until the mapping names them; assigning the task again after adding it records the person. An admitted Work Item acts for its admission's `X-Ploeg-Acting-User`, else its `X-Ploeg-Actor`.

Ploeg deduplicates every tracker and forge webhook ([ADR-0173](../adrs/0173-a-webhook-delivery-is-claimed-under-a-lease-and-marked-seen-only-after-its-effects-commit.md)). It claims a delivery before acting and marks it complete after every effect succeeded, so a redelivery of a completed delivery is answered 202 and does nothing, a copy that arrives while the first is still acting is answered 409, and a delivery that failed or whose handler crashed acts again. Vikunja and ClickUp send no delivery id, so the provider derives one from the signed payload: for Vikunja the event name, task, project, assignee, related task and the payload's `time` (else the task's `updated`); for ClickUp the event name, task, history item ids and the latest history item date. A payload without either time is not deduplicated. GitLab is keyed on `Idempotency-Key`, else on its object kind, project, object id, action or status and `updated_at`. Ids are kept 48 hours ([data retention](data-retention.md)).

Before expecting an assignment to dispatch work, verify the actual tracker project, the assignee's access, webhook registration, provider routing and target mapping. A planning board and an execution test board may be different projects.

When the Vikunja URL and token are configured, ploegd checks webhook registration itself at startup and then hourly. For every Vikunja project in the routing config it lists the project's webhooks and looks for one that sends `task.assignee.created` to Ploeg: exactly `PLOEG_VIKUNJA_WEBHOOK_URL` when that is set, otherwise any target on the `/webhooks/tracker/vikunja` path. A project without one is logged as a warning naming the project. The unauthenticated `GET /readyz` reports only counts, under `vikunjaWebhooks.missingProjects` and `uncheckedProjects` (projects the check could not read). Readiness stays healthy, because one silent board does not stop the service. Setting `PLOEG_VIKUNJA_WEBHOOK_REGISTER=true` additionally registers a signed webhook on each missing project; it requires `PLOEG_VIKUNJA_WEBHOOK_URL` and the webhook secret, and ploegd refuses to start without them. Registration writes tracker state, so decide first whether each configured board should dispatch at all.

When the ClickUp token and `PLOEG_CLICKUP_WORKSPACE_ID` (chart `tracker.clickup.workspaceId`) are set, ploegd checks the configured ClickUp Lists the same way, at startup and hourly, through the tracker port's `WebhookChecker` capability ([ADR-0183](../adrs/0183-ploegs-core-reaches-trackers-and-forges-only-through-ports-and-every-adapter-passes-its-ports-conformance-suite.md)). It lists the Workspace's webhooks (`GET /team/{workspace}/webhook`, which shows only webhooks the token's user created), reads each List's Folder and Space, and looks for a webhook whose location covers the List and that sends `taskAssigneeUpdated`, `taskStatusUpdated` and `taskUpdated` (or `*`) to `PLOEG_CLICKUP_WEBHOOK_URL`, or to any endpoint on `/webhooks/tracker/clickup` when that is unset. A webhook ClickUp has `suspended` does not count. `/readyz` reports the counts under `clickupWebhooks`, and the connections view reports each List's webhook and the List's members. Ploeg verifies every ClickUp delivery with the one `PLOEG_CLICKUP_SECRET`, so use one Workspace-wide webhook. `PLOEG_CLICKUP_WEBHOOK_REGISTER=true` is refused at startup: ClickUp returns a new webhook's signing secret in the create response, and this release has no secret store to hand it to. The ClickUp adapter registers through a `WebhookSecretSink` and deletes the webhook again when the sink refuses the secret; the store behind it is not built yet. Until then, create the webhook yourself and put its secret in `PLOEG_CLICKUP_SECRET`.

ClickUp moves a task only to List statuses you name, through `PLOEG_CLICKUP_STATUS_MAP` (chart `tracker.clickup.statuses`). For Lists with the statuses Backlog, Ready, In progress, In review and Done, set `active=In progress,awaiting_review=In review,done=Done`: ploegd writes `active` when it opens a Shift on the item, `awaiting_review` when the Shift ends with a pull request to review, and `done` only when the item is finished and `done` is mapped. Backlog and Ready stay the person's to set. Names are matched to the task's List without regard to case or surrounding space, and the List's own spelling is written; a task already in that status is not written again. Every List the map is used on must have each named status, or ClickUp refuses the write and ploegd logs it. Vikunja and GitHub Issues ignore every state but `done`. Status writes are tested against a fake ClickUp only.

On ClickUp, any assignee dispatches by default, so a person assigning themselves on a routed List would start paid work. Production boards should name the members that hand work to Ploeg in `trackers.clickup.agents` (usernames or email addresses, compared without case). With it set, ploegd ignores assigning or unassigning anyone else, and an agent member's assignment runs as the List's pinned `team`, else as the agent member's Team under `teams.<name>.assignees`, else `PLOEG_DEFAULT_TEAM`. Unset keeps dispatch on every assignee. ploegd refuses `agents` under another tracker.

```yaml
trackers:
  clickup:
    agents: [agent-member]
    projects:
      - {name: "Product", id: "901234567", default: app, team: bronze}
```

A person names the Team for one task in a dropdown custom field on the task ([ADR-0187](../adrs/0187-a-team-is-assignable-in-a-tracker-as-a-delegate-and-reports-its-work-as-a-session-of-activities.md), the ClickUp emulation of a tracker's own agent delegate). The field is called `Team` unless `PLOEG_CLICKUP_TEAM_FIELD` (chart `tracker.clickup.teamField`) names another, matched without regard to case, and its selected option is the Team name, lower-cased. A set field wins over the List's pinned `team` and over the agent member's Team; the pin and the assignee mapping stay the fallback for a task whose field is unset or absent, so a board without the field keeps working as before. A field that names a Team this installation does not have is refused at intake like a bad `repo/` label: nothing is queued, the refusal is recorded with the code `team_unknown` under the List's Team, and ploegd comments on the task naming the value it read and the Teams it has, so the person corrects the field and assigns again. The ClickUp adapter declares this as the `agent_identity` capability, reads the field from the same task read that mirrors the item, and renders a Team's activities and links as comments. Unassigning the agent member withdraws the work whichever way its Team was chosen.

Create the field by hand, once per Space or Workspace so every dispatching List shares it: in ClickUp open the List, choose **Custom Fields** → **Dropdown**, name it `Team` (or the name you configured) and add one option per Team name of this installation, spelled as under `teams:` (case does not matter). ploegd does not create or sync the field in this release.

## What Ploeg says on the card

Once a Team is chosen and the repository resolved, intake runs the fit gate of [ADR-0187](../adrs/0187-a-team-is-assignable-in-a-tracker-as-a-delegate-and-reports-its-work-as-a-session-of-activities.md) before anything is queued: checks on facts ploegd already holds, no model call, no sandbox. Its answer is the first thing the card gets from Ploeg, as an activity through the tracker's `agent_identity` capability when it declares one (on ClickUp a comment; a thought is a plain note, an error opens with _Not starting_ and a question with _Question_), else as a plain comment. Exactly one of these four appears, once per hand-over; a webhook redelivery and a re-assignment of a card that is already queued or active add nothing.

| When | Kind | The card reads |
| --- | --- | --- |
| Every check passed and the card was queued | `thought` | `Team bronze takes this card.` then `Repository webgrip/app, base branch main.` (when routing resolved one), then `Budget left this week: US$ 3.00 of US$ 5.00.` (when the Team has a `spendCap`), then `The pull request link lands here when the work is ready for review.` |
| The Team's plan has no writing Role (`team_cannot_write`) | `error` | `Team silver has no Role that writes code.` then `Teams that can take it: bronze.` or `No configured Team can take it.` |
| The Team's settled and held spend has reached its `spendCap` (`budget_exhausted`) | `error` | `Team bronze has spent US$ 5.00 of its US$ 5.00 this week; it can take this card again from Monday 2 November 2026.` then the Teams line |
| A Role of the Team runs OpenHands and the repository ships `.openhands/hooks.json` (`harness_refuses_repository`) | `error` | `Team bronze runs OpenHands for its builder Role, and OpenHands refuses a repository that ships .openhands/hooks.json, which webgrip/app does.` then the Teams line |
| No Team at all: the field is unset, the List has no pin, the assignee maps to no Team and `PLOEG_DEFAULT_TEAM` is empty (`team_missing`) | `elicitation` | `Which Team should take this card? Set the Team field. Teams that can take this repository: bronze, silver.` (the field name is the one the tracker configured) |

A refusal is recorded like a routing refusal, with its code under the Team the work would have run as, so `GET /api/v1/operator/route-refusals` lists it; `team_missing` has no Team and is listed for a consumer that reads every Team. "Teams that can take it" names the other configured Teams whose routing lands this card in the same repository and that pass the same checks. `PLOEG_DEFAULT_TEAM` defaults to `default`, so the question only arises on an installation that set it empty. Routing refusals (`label_missing`, `target_not_ready` and the rest) keep their own comment.

What the gate checks at intake and what still happens later:

- **Writing Role** — at intake, from the Team's plan (a plan-less Team under uniform dispatch has one writer). A Team the engine does not dispatch is not judged here.
- **Repository for the Team** — the routing rules of [ADR-0038](../adrs/0038-a-repo-label-selects-among-registered-targets-and-the-board-default-is-the-fallback.md) and the readiness gate already refuse this at intake; nothing was added.
- **Budget headroom** — at intake, when the Team has a `spendCap`: refused only when settled plus held spend has reached the cap, since the card's own cost is not estimated. The claim-time check of [ADR-0162](../adrs/0162-a-team-spends-at-most-its-cap-per-period-and-a-claim-over-it-starts-nothing.md) still decides each Run.
- **Harness enters the repository** — at intake only when `PLOEG_TEAM_HARNESSES` names the Team's Harness per Role and the resolved target is registered, from the readiness gate's last inspection of the repository (forge adapters report the hooks file beside `AGENTS.md`). Without that configuration the worker's refusal at `Prepare` ([ADR-0148](../adrs/0148-every-acp-profile-asks-before-a-mutation-outside-allow-always-and-openhands-refuses-a-repository-that-ships-hooks.md)) stays the only check. A harness missing from a Team's allowlist is not checked at intake.
- **Not at intake** — the premise check runs on the sweep, as above; the dependency hold too; a Role bound to no model or Harness, and a Team without a sponsor, are refused when the Run claims ([ADR-0156](../adrs/0156-each-run-carries-a-transaction-token-that-names-its-person-and-a-team-without-a-sponsor-runs-nothing.md)); the starting thought carries no estimate.

A ClickUp Work Item's branch is `agent/CU-<task id>` and its commit trailer and pull request reference are `CU-<task id>`, the form ClickUp's GitHub and GitLab integrations recognise, so they attach the pull request to the task. The ClickUp adapter supplies the format through its `ReferenceNamer` capability, which ploegd and ploeg-worker both register at start. A Shift keeps the branch it recorded when it opened, and a requeued Work Item keeps its previous Shift's branch; a new Shift on an item that last ran under the earlier `agent/clickup-<id>` form gets the new name. Vikunja items keep `agent/vik-<id>` and `VIK-<id>`.

The [July board snapshot](https://forgejo.webgrip.dev/webgrip/ploeg/src/commit/94c7c8e2dc07037ee2fd38a69343426e40bd680d/docs/ops/board.md) records IDs and MCP failures observed then. Do not treat those IDs, counts, API errors or the old console default as current configuration.
