# Tracker configuration and historical board notes

The tracker owns current work and priorities. Ploeg receives configured provider events and resolves a Work Target from the registered Scope. An operator consumer registers its own task sources and repository mapping; there is no universal project-ID default.

For current integration behavior, read [tracker execution binding](../contracts/tracker-execution.md), the [Vikunja provider](../../pkg/provider/vikunja/vikunja.go), the [ClickUp provider](../../pkg/provider/clickup/clickup.go) and the [GitHub Issues provider](../../pkg/provider/githubissues/githubissues.go). To connect GitHub Issues, follow [Connect GitHub Issues](../how-to/connect-github-issues.md); it dispatches on a `ploeg:<team>` label rather than an assignee, and ploegd does not check or register its webhooks.

To have agents implement an OpenSpec change, put a line `openspec: <change-id>` in the tracker item's description. See [OpenSpec Work Items](../contracts/README.md#openspec-work-items) for what the Run then does.

A queued Work Item waits before its first Shift while its tracker says it waits for an item that is not done ([ADR-0123](../adrs/0123-dispatch-waits-for-tracker-dependencies-and-an-opt-in-free-premise-check.md)). On Vikunja that is a "blocked by" or "follows" relation; on GitHub Issues a "blocked by" issue dependency; on ClickUp a task the item is "waiting on", done when its status is of the closed or done type. ploegd reads the relations when it would open the Shift and again every `PLOEG_DEPENDENCY_RECHECK` (default `5m`) while the item waits, and the operator API lists the open ones under the Work Item's `waitingFor`. `PLOEG_DEPENDENCY_HOLD=false` switches the hold off. A tracker that cannot be read holds nothing new.

A Team with `teams.<name>.premiseCheck.model` set gets one classifier call on that gateway model before its first writer, from the next sweep. ploegd reads the model's price from LiteLLM first and makes no call unless every deployment of it costs nothing, mints a key that reaches only that model with fallbacks disabled, and refuses a reply the gateway charged for. `proceed` opens the Shift. `ask` and `too_big` move the Work Item to `needs_human`, comment the question on the tracker task and spend nothing on a writer; assigning the task again sends it on without a second check. After three failed attempts the check is recorded as `skipped` and dispatch goes on.

A Role whose `claude-environment` Runs a client carries (chart `harness.claudeEnvironment.carrier: client`, [ADR-0112](../adrs/0112-a-claude-environment-run-uses-the-claude-login-of-the-person-it-acts-for.md)) gets no worker. Its Work Item waits as `needs_human` with `waitingForClient` (reason `start_from_claude_code`) until the person it acts for claims the Run with `POST /api/v1/operator/work-items/{id}/claim` and dispatches it with their own Claude Code. For tracker work that person is the tracker user who assigned it, mapped to Ploeg's person id in `trackers.<tracker>.people` (`{<username>: <person id>}`, compared without case). An unmapped user's work waits, naming the tracker user, until the mapping names them; assigning the task again after adding it records the person. An admitted Work Item acts for its admission's `X-Ploeg-Acting-User`, else its `X-Ploeg-Actor`.

Ploeg deduplicates every tracker and forge webhook ([ADR-0173](../adrs/0173-a-webhook-delivery-is-claimed-under-a-lease-and-marked-seen-only-after-its-effects-commit.md)). It claims a delivery before acting and marks it complete after every effect succeeded, so a redelivery of a completed delivery is answered 202 and does nothing, a copy that arrives while the first is still acting is answered 409, and a delivery that failed or whose handler crashed acts again. Vikunja and ClickUp send no delivery id, so the provider derives one from the signed payload: for Vikunja the event name, task, project, assignee, related task and the payload's `time` (else the task's `updated`); for ClickUp the event name, task, history item ids and the latest history item date. A payload without either time is not deduplicated. GitLab is keyed on `Idempotency-Key`, else on its object kind, project, object id, action or status and `updated_at`. Ids are kept 48 hours ([data retention](data-retention.md)).

Before expecting an assignment to dispatch work, verify the actual tracker project, the assignee's access, webhook registration, provider routing and target mapping. A planning board and an execution test board may be different projects.

When the Vikunja URL and token are configured, ploegd checks webhook registration itself at startup and then hourly. For every Vikunja project in the routing config it lists the project's webhooks and looks for one that sends `task.assignee.created` to Ploeg: exactly `PLOEG_VIKUNJA_WEBHOOK_URL` when that is set, otherwise any target on the `/webhooks/tracker/vikunja` path. A project without one is logged as a warning naming the project. The unauthenticated `GET /readyz` reports only counts, under `vikunjaWebhooks.missingProjects` and `uncheckedProjects` (projects the check could not read). Readiness stays healthy, because one silent board does not stop the service. Setting `PLOEG_VIKUNJA_WEBHOOK_REGISTER=true` additionally registers a signed webhook on each missing project; it requires `PLOEG_VIKUNJA_WEBHOOK_URL` and the webhook secret, and ploegd refuses to start without them. Registration writes tracker state, so decide first whether each configured board should dispatch at all.

When the ClickUp token and `PLOEG_CLICKUP_WORKSPACE_ID` (chart `tracker.clickup.workspaceId`) are set, ploegd checks the configured ClickUp Lists the same way, at startup and hourly, through the tracker port's `WebhookChecker` capability ([ADR-0183](../adrs/0183-ploegs-core-reaches-trackers-and-forges-only-through-ports-and-every-adapter-passes-its-ports-conformance-suite.md)). It lists the Workspace's webhooks (`GET /team/{workspace}/webhook`, which shows only webhooks the token's user created), reads each List's Folder and Space, and looks for a webhook whose location covers the List and that sends `taskAssigneeUpdated`, `taskStatusUpdated` and `taskUpdated` (or `*`) to `PLOEG_CLICKUP_WEBHOOK_URL`, or to any endpoint on `/webhooks/tracker/clickup` when that is unset. A webhook ClickUp has `suspended` does not count. `/readyz` reports the counts under `clickupWebhooks`, and the connections view reports each List's webhook and the List's members. Ploeg verifies every ClickUp delivery with the one `PLOEG_CLICKUP_SECRET`, so use one Workspace-wide webhook. `PLOEG_CLICKUP_WEBHOOK_REGISTER=true` is refused at startup: ClickUp returns a new webhook's signing secret in the create response, and this release has no secret store to hand it to. The ClickUp adapter registers through a `WebhookSecretSink` and deletes the webhook again when the sink refuses the secret; the store behind it is not built yet. Until then, create the webhook yourself and put its secret in `PLOEG_CLICKUP_SECRET`.

ClickUp moves a task only to List statuses you name, through `PLOEG_CLICKUP_STATUS_MAP` (chart `tracker.clickup.statuses`). For Lists with the statuses Backlog, Ready, In progress, In review and Done, set `active=In progress,awaiting_review=In review,done=Done`: ploegd writes `active` when it opens a Shift on the item, `awaiting_review` when the Shift ends with a pull request to review, and `done` only when the item is finished and `done` is mapped. When `PLOEG_REPORT_WORK_ITEM_URL` names where a Work Item is followed (chart `env.PLOEG_REPORT_WORK_ITEM_URL`, `{id}` filled with the Work Item id), opening a Shift also comments that link on the task, on every tracker, so a person can open the work from the card; unset, the status write is all the task hears until the Shift closes. Backlog and Ready stay the person's to set. Names are matched to the task's List without regard to case or surrounding space, and the List's own spelling is written; a task already in that status is not written again. Every List the map is used on must have each named status, or ClickUp refuses the write and ploegd logs it. Vikunja and GitHub Issues ignore every state but `done`. Status writes are tested against a fake ClickUp only.

On ClickUp, any assignee dispatches by default, so a person assigning themselves on a routed List would start paid work. Production boards should name the members that hand work to Ploeg in `trackers.clickup.agents` (usernames or email addresses, compared without case). With it set, ploegd ignores assigning or unassigning anyone else, and an agent member's assignment runs as the List's pinned `team`, else as the agent member's Team under `teams.<name>.assignees`, else `PLOEG_DEFAULT_TEAM`. Unset keeps dispatch on every assignee. ploegd refuses `agents` under another tracker.

```yaml
trackers:
  clickup:
    agents: [agent-member]
    projects:
      - {name: "Product", id: "901234567", default: app, team: bronze}
```

A ClickUp Work Item's branch is `agent/CU-<task id>` and its commit trailer and pull request reference are `CU-<task id>`, the form ClickUp's GitHub and GitLab integrations recognise, so they attach the pull request to the task. The ClickUp adapter supplies the format through its `ReferenceNamer` capability, which ploegd and ploeg-worker both register at start. A Shift keeps the branch it recorded when it opened, and a requeued Work Item keeps its previous Shift's branch; a new Shift on an item that last ran under the earlier `agent/clickup-<id>` form gets the new name. Vikunja items keep `agent/vik-<id>` and `VIK-<id>`.

The [July board snapshot](https://forgejo.webgrip.dev/webgrip/ploeg/src/commit/94c7c8e2dc07037ee2fd38a69343426e40bd680d/docs/ops/board.md) records IDs and MCP failures observed then. Do not treat those IDs, counts, API errors or the old console default as current configuration.

## Team identity

A Team has three identifiers ([ADR-0198](../adrs/0198-a-team-has-an-immutable-id-a-renameable-key-and-a-free-name-and-a-proven-person-creates-one-at-runtime.md)). Its **key** is its name under `teams.<key>` in the configuration file. Its **id**, `team_` and a lowercase ULID, is what ploegd stores: on the first boot of a release that has it, ploegd gives every static Team an id, records `team.created` attributed to `configuration`, and backfills `team_id` on Work Items, Shifts, Runs, leases, chats, premise checks and tracker bindings in batches of 10,000 rows, after boot, without holding up readiness. One ploegd backfills at a time (a session advisory lock; another replica logs that it left the backfill to the one holding it). Each batch locks its rows in key order and skips rows that live work holds, so it never waits on or deadlocks with dispatch. A table whose pass skipped nothing is recorded in `team_id_backfills` and not scanned again; reconciliation clears that record whenever a Team takes a key or alias it did not hold, so rows written under a key before it had a Team are still filled. A row written after that takes its `team_id` from its Team's key, unless the row belongs to a tenant: a tenant's row (a tracker binding with a `tenant`, an audit row whose detail names one) never takes a static Team's id by key. An update that moves a row to a key without a static Team keeps a runtime Team's `team_id` rather than clearing it. Audit rows that name a Team gain `detail.team_id`. Its **name** is display text: `teams.<key>.name`, or `<role> · <harness>` for a one-Role Team that sets none, and the key otherwise.

Keys and aliases compare without case, so the file may not hold two keys that differ only in case (`Builders` and `builders`); ploegd refuses to load it. An alias may move from one Team to another in one change: ploegd releases every key and alias that leaves a Team before any Team takes one.

To rename a static Team without losing its id, change its key and list the old one under `teams.<new-key>.aliases` (at most 10) in the same change; ploegd keeps the id and writes `team.renamed`. A Team whose key changes without that alias is a new Team with a new id, and the old one is removed with `team.removed`; if its key comes back, the old id returns. When a key leaves the file in the same boot that a new key with the same configuration (everything but `name` and `aliases`) appears, ploegd logs a warning naming both keys and suggesting `teams.<new-key>.aliases: [<old-key>]`, and records `team.rename_suspected` with `from` and `from_team_id`. Adding the alias afterwards makes the old key resolve to the new Team; it does not bring back the old id.

`GET /api/v1/operator/teams` and `GET /api/v1/operator/teams/{team}` carry `teamId`, `key`, `aliases`, `name`, `source`, `state` and `nameSource`; `{team}` may be an id, a key or an alias, and a request by alias answers with `Content-Location` naming the key. `id` stays the key in this schema version. The configuration file is the only source of a static Team's name, and `nameSource` says so with the file key, so `PATCH /api/v1/operator/teams/{team}` with a `name` answers `409 name_set_by_configuration` naming `teams.<key>.name` and records `team.refused`. Every Team metric carries `team_id` beside `team`; `ploeg_team_info{team_id,key,source,state}` joins a key onto an id, and `ploeg_teams{source,state}` counts Teams.

### Upgrading to Team identity

- Every series of a Team metric (`ploeg_shifts_open`, `ploeg_runs_finished_total`, `ploeg_team_period_spend_usd` and the other metrics labelled `team`) gains a `team_id` label for a Team that has an id, from the release that contains migration 0090 (`v0.2.0-rc.117` onwards). A boot whose Team reconciliation fails serves the same series without `team_id` until the next boot. A dashboard, recording rule or alert that matches an exact label set, joins on labels with `on(...)` or `ignoring(...)`, or aggregates `by` every label must add `team_id` or aggregate it away; one that selects by `team` keeps working. Each series also changes identity once, at the upgrade, so a `rate()` or `increase()` across the upgrade restarts.
- Migration 0090 blocks reads and writes of seven tables while it runs; see [locks a migration holds](compatibility.md#locks-a-migration-holds) and plan a short window.
## Runtime Teams

A proven person creates, changes and removes Teams while ploegd runs ([ADR-0198](../adrs/0198-a-team-has-an-immutable-id-a-renameable-key-and-a-free-name-and-a-proven-person-creates-one-at-runtime.md)). Four gates apply together: `config.teamCreation.enabled` with the `models` a Role may name, `may`, `maxRoleCap`, `max` (default 10 per Tenant) and `tenants.<tenant>.spend`, the allowance the caps of a Tenant's runtime Teams add up to; the consumer's `manageTeams`; a proven person in every attribution mode, asserted included, with the claims `requireClaims` names; and a pool for each Harness. Changing only a runtime Team's `name` follows the installation's attribution mode.

`POST /api/v1/operator/teams` takes the manifest (`key`, `name`, `charter`, `plan` with each Role's `harness` and `model`, a required `spend.cap`, `maxRunning`, `may`, `intake`, `sponsor`, which defaults to the person creating it) and answers `201`, or `200` for the same key and body; `?dryRun=true` writes nothing and reports the state and the spend headroom left. A field that would change a pod, a credential or a network path (`image`, `dind`, `sandbox`, `toolchains`, `claudePlugins`, MCP groups, `tools`, `skills`, `assignees`, a repository) or any unknown field answers `422 field_not_allowed` naming it. `PUT /teams/{team}` with `If-Match` replaces the manifest; a changed key is a rename, and the old key stays an alias. `DELETE /teams/{team}/aliases/{alias}` releases one, and a released alias or a removed Team's key stays reserved for 90 days (`409 key_reserved`, and `404 unknown_team` with `reservedUntil` on a read). `DELETE /teams/{team}` answers `409 team_in_use` while a binding, an open Work Item or a static `refinementTeam` names the Team; `?drain=true` refuses new work, removes the Team when its last Work Item ends, and after 14 days moves the open Work Items to `needs_human` with `team_drain_expired` and removes it. `POST /teams/{team}/undrain` cancels a drain.

A static Team always wins: a key the file adds later shadows the runtime Team that held it (`team.shadowed`), its pending Runs are not claimed and its bindings turn `invalid` with `team_unavailable`, until the static key goes away. A runtime Team Ploeg can no longer run turns `invalid` with the cause (`harness_not_offered`, `harness_not_qualified`, `model_not_allowed`, `target_unavailable`, `spend_exceeds_tenant`, `creation_disabled`) and returns to `active` by itself. ploegd re-decides states at boot and every minute.

Work reaches a runtime Team two ways. An operator Admission may name it by id, key or alias when its `intake.admissions` is true, on a target its `intake.targets` lists (any target when the list is empty); a shadowed or invalid Team answers `409 team_unavailable`, a draining one `409 team_draining`. A tracker binding may name it when `config.teamCreation.trackerBindings` sets the connections and limit every runtime Team accepts, which a consumer with `manageTeams` uses without naming the Team in its scope. The Shift engine plans a runtime Team's Work Items from its manifest, and each Run stores its Role's Harness and model, so only that Harness's pool claims it.

Runtime Teams run on generic worker pools: `executor.runtimeTeams.pools` renders one ScaledJob per Tenant and isolation-qualified Harness, with the Harness's default image and no DinD, and ploegd learns them from `PLOEG_RUNTIME_POOLS`. A pool worker reads the bootstrap Secret key `pool--<tenant>--<harness>`; add `{"token": "...", "pool": {"tenant": "...", "harness": "..."}}` to the bootstrap registry. Its claim selects the oldest pending Run of an active runtime Team of the Tenant on the Harness, below the Team's `maxRunning` and spend cap, and never a static Team's Run; a static Team's worker never claims a runtime Team's Run. `isolation: gateway` marks a pool the credential gateway of ADR-0197 will serve; until that chart lands, a gateway pool still needs both credential proxies on.

## Runtime Scope bindings

Routing has two sources ([ADR-0186](../adrs/0186-an-operator-consumer-binds-a-tracker-scope-to-a-team-at-runtime-and-static-routing-wins-on-conflict.md)): the static `trackers.<tracker>.projects` in the configuration file, and Scope bindings an operator consumer adds while ploegd runs. `GET /api/v1/operator/tracker-bindings` lists both, so read it, not the file alone, to know what feeds a Team.

A Team accepts bindings only when its manifest opts in:

```yaml
teams:
  silver:
    trackerBindings:
      connections: [clickup]   # a configured tracker by kind; "*" or "*:<kind>" match store-backed connections only
      max: 20                  # live bindings, default 20
```

The consumer needs `bindScopes: true` in `PLOEG_OPERATOR_CONSUMERS` (chart `operator.consumers[].bindScopes`) and the Team in its scope, and every change needs an actor, a proven person under `PLOEG_OPERATOR_ATTRIBUTION=proven`. `POST /api/v1/operator/teams/{team}/tracker-bindings` probes the Scope through the adapter's `ScopeProber` (and `ScopeNamer` for a name) before it stores anything; `?dryRun=true` probes only. Today only the ClickUp adapter declares them, so a Vikunja or GitHub binding answers `422 capability_missing`. A binding selects registered targets with `default` and `allow` and never names a repository.

Static routes win. A binding for a Scope a static route already decides is refused with `409 conflicts_with_static`; a static route added later marks the binding `shadowed`, takes it out of routing and writes `tracker_binding.shadowed`, and removing the static route brings it back. A binding whose Team leaves the file, or whose target key leaves the effective registry, turns `invalid`. A binding without a confirmed webhook is `awaiting_webhook`: it routes, and ploegd checks its Scope's webhook again every hour. With a connection secret store configured and `PLOEG_CLICKUP_WEBHOOK_URL` or `PLOEG_PUBLIC_WEBHOOK_BASE` set, ploegd instead registers a webhook for the bound List, keeps its signing secret under `webhooks/clickup/<id>`, verifies that webhook's deliveries with it, and the binding starts `active`. Bindings on one List share that webhook, and it is deleted with the last of them. `"*"` and `"*:<kind>"` admit store-backed connections in state `active`; ingest through a store-backed connection's own credential is not built yet. `ploeg_tracker_bindings{state}` counts them for alerts.

Each ploegd rebuilds its routing table after every change it makes and reads the highest binding revision every 30 seconds, so a second replica follows within 30 seconds. If the bindings cannot be read at boot, the static routes alone load and the poll retries.
