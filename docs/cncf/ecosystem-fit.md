# Ecosystem fit

This page compares Ploeg with the projects a CNCF reviewer is likely to put next to it, and says which of them Ploeg uses, which it could use, and which it competes with. It answers [issue #32](https://github.com/ploeg-hq/ploeg/issues/32). The [Day 0 review](day-0.md) explains Ploeg's own design, and the [application draft](application-draft.md) reuses this page for the form's overlap and similar-projects questions.

Everything below is as of **2026-10-27**. Each row names the release or commit it was read at. Agent projects in this space ship weekly, so a row older than a month should be read again before anyone quotes it.

Two kinds of statement appear here, and they are kept apart:

- **Observed**: read in the project's source or documentation at the named commit, or seen in a run.
- **Proposed**: a design record or roadmap item that is not yet shipped. Ploeg's own proposed ADRs are marked *proposed*.

Ploeg is not the only system that runs AI coding agents on Kubernetes, and this page does not claim it is.

## What Ploeg owns and what it consumes

Ploeg decides whether a piece of agent work may run, pays for it from an authorized budget, gives one worker at a time a lease on it, mints that worker's credentials for that Run only, and records what happened. It does not run models, does not isolate processes itself and does not write the agent.

| Layer | Ploeg's position | Projects in that layer |
| --- | --- | --- |
| Work intake | Owns admission from trackers (Vikunja, ClickUp, GitHub Issues) and from authenticated operator clients | Hive Commons, kagent ScheduledRuns |
| Authorization, budget, lease | **Owns.** Budget authorized before a Run and settled afterwards from the gateway's spend logs; PostgreSQL leases with expiry | Hive Commons (rolling token budget), kagent (usage reporting) |
| Scaling worker count | Consumes KEDA | KEDA |
| Placement and isolation | Consumes Kubernetes Jobs, RuntimeClass (gVisor, Kata) and, experimentally, agent-sandbox | agent-sandbox, Agent Substrate, OpenShell |
| The agent itself | Consumes harnesses through adapters: ACP (OpenCode, Qwen Code, Goose), OpenHands, Claude Code, `exec` | OpenHands, OpenCode, Claude Code, kagent Harnesses |
| Model access and metering | Consumes LiteLLM virtual keys, minted per Run | LiteLLM, Agent Router (formerly Envoy AI Gateway) |
| Delivery | Owns reading delivery facts from the forge (GitHub, Forgejo, GitLab in part); a person merges | Hive Commons (GitHub) |
| Client protocols | Serves its operator reads as MCP tools; speaks ACP to agents; watches A2A | MCP, ACP, A2A |

## Where others are ahead

A reviewer should not have to dig for these:

- **Adoption.** Ploeg has no adopters outside its maintainer and no GitHub stars on this date. Hive Commons publishes adopters and measured outcomes; kagent has 4,109 stars.
- **Maintainers.** Ploeg has one maintainer ([eligibility](eligibility.md)), which blocks filing.
- **CNCF standing.** Hive Commons, kagent, Agent Substrate and OpenShell have passed a TOC vote. Ploeg has not applied.
- **Isolation.** Agent Substrate and OpenShell enforce isolation and egress themselves. Ploeg relies on Kubernetes, the RuntimeClass and the installer's CNI, and an open finding (F-41) records that seccomp was off inside the Kata guest in the one tested cluster.
- **Kubernetes API shape.** kagent and agent-sandbox model their objects as CRDs. Ploeg's configuration is Helm values and environment, and its work state is in PostgreSQL behind an HTTP API, with no CRDs.
- **Harness and tracker breadth.** Hive Commons drives more agent CLIs and reads Linear and Jira, which Ploeg does not.

## What Ploeg contributes

The reusable part is a contract for paying for and owning agent work, kept apart from how the agent is isolated and which agent it is:

1. **Budget authorized before a Run and settled after it** from the gateway's own spend logs, never below what Ploeg observed, with unknown spend left unresolved until trusted reconciliation ([ADR-0012](../adrs/0012-two-level-budgets-authorized-and-settled.md), [ADR-0155](../adrs/0155-an-operator-settles-an-account-the-gateway-cannot-answer-for-from-evidence-and-never-below-what-ploeg-observed.md)).
2. **One owner per Work Item branch** through a PostgreSQL lease that the controller expires, so safety never depends on a dying agent cleaning up.
3. **Credentials minted per Run**, for one model and one repository, that the agent's container never holds ([ADR-0138](../adrs/0138-a-harness-runs-in-its-own-container-and-no-credential-enters-it.md)).
4. **Delivery facts read from the forge**, never from the agent, and a person merges.
5. **Published, versioned contracts** for each seam: the executor SPI any launcher can implement, the run API, the operator API and the Task Spec and Outcome Report a harness adapter speaks ([contracts](../contracts/README.md)).

Hive Commons has its own answers to 2, 3 and 4, and kagent and Agent Substrate to 3. The authorize-then-settle accounting and the executor contract that lets KEDA, a CronJob or agent-sandbox launch the same Run are the parts we have not found elsewhere in the projects above.

## When to read this again

- Hive Commons adds Forgejo or GitLab, per-Run Kubernetes execution or spend refused per task. Ploeg's distinct ground would then shrink to the accounting contract, and [ADR-0005](../adrs/0005-build-a-dedicated-dispatch-plane.md)'s trigger about a lease-based dispatcher with more than one maintainer should be reopened.
- kagent adds a tracker or forge trigger, or a budget it enforces.
- Agent Substrate or OpenShell reaches 1.0 with a Kubernetes path that a Ploeg executor could claim from.
- ACP v2 leaves alpha.
- The CNCF opens a TAG or working group for agent workloads. As of this date AI is a Technical Community Group, not a TAG ([day-0](day-0.md#where-ploeg-fits-in-the-cncf)).
