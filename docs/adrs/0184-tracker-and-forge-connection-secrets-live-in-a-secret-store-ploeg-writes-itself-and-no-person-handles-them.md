# Tracker and forge connection secrets live in a secret store Ploeg writes itself, and no person handles them

## Context and Problem Statement

Every tracker and forge connection needs at least two secrets: a credential Ploeg uses to read and write the system, and the signing secret that proves a webhook delivery came from it. Today a person seeds both by hand, as environment variables or as Kubernetes Secrets named in Helm values (`trackers.clickup.tokenSecret`, `trackers.clickup.webhookSecret` and their siblings in `ops/helm/ploeg/values.yaml`). For ClickUp the chart's own note says the webhook secret is generated by ClickUp and returned once, in the create-webhook response, so a person must register the webhook, catch the secret from the response and paste it into a Secret before deliveries verify. Registering a webhook therefore needs a person in the loop, and every secret passes through someone's clipboard, terminal history or laptop. Where should connection secrets come from and where should they live, so that connecting a tracker or forge needs no person to handle a secret?

## Decision Drivers

* No person handles a secret value: not when connecting, not when registering a webhook, not when reconnecting.
* A webhook secret that the vendor returns once must be captured by the party that made the call, at the moment it is returned.
* Ploeg's database, logs, API responses and events are read by many parties (operator consumers, dashboards per [give dashboards read access](../how-to/give-dashboards-read-access.md), backups); a secret in any of them is a secret spread wide.
* Installations differ: some run OpenBao or Vault, some only Kubernetes.
* Adapters are named in one place and selected by configuration, as trackers and forges already are (ADR-0183, proposed in [ploeg-hq/ploeg#393](https://github.com/ploeg-hq/ploeg/pull/393)).
* Existing installations configured through environment variables and Helm Secrets must keep working unchanged.

## Considered Options

* **Ploeg obtains the credential by OAuth and writes every connection secret into a pluggable secret store; its own records carry only a reference**
* Ploeg seals connection secrets in its own database with envelope encryption
* Ploeg only reads secrets a person has put in a vault, by reference

## Decision Outcome

Chosen option: "**Ploeg obtains the credential by OAuth and writes every connection secret into a pluggable secret store**", because it is the only option in which the party that receives each secret is the party that stores it, so no person and no consumer ever holds one, while the value still lives in a system built to keep it.

1. **The credential comes from OAuth.** Where the tracker or forge offers an OAuth authorization-code flow, the person grants access on the vendor's consent page. The operator consumer that started the flow relays the one-time authorization code to Ploeg's operator API, authenticated as every operator change is ([ADR-0150](0150-an-operator-consumer-proves-the-person-it-acts-for-with-a-token-exchanged-for-ploegs-audience.md), [ADR-0171](0171-an-operator-change-needs-a-proven-person-and-the-chart-refuses-asserted-attribution-from-0-3-0.md)). Ploeg holds the OAuth client secret and performs the code exchange itself, so the consumer never sees the access token. The pattern is the one ADR-0094 uses for a Team's Claude login: the consumer carries only a one-time code. Pasting a token stays possible as a fallback for a system without OAuth, and the pasted value goes straight to the store under the same rules.
2. **Ploeg writes the secrets into a secret store.** A `SecretStore` port with `Put`, `Get` and `Delete` by reference has adapters registered in the one adapter table, like trackers and forges. Ploeg writes the access token and, when it registers the webhook, the webhook signing secret: the one the vendor returns once at creation (ClickUp), or one Ploeg generates itself where the vendor accepts a chosen secret (Forgejo, GitHub, GitLab). The first adapter is OpenBao or Vault KV v2, authenticated with Kubernetes auth under a policy that allows Ploeg only its own path. The second is a Kubernetes Secret adapter for installations without a vault, limited by a namespaced Role to Secrets Ploeg created. Ploeg's database, logs, API responses and events never contain a value; they carry a reference (store, path, version).
3. **Reconnect and disconnect are complete.** Reconnecting runs the same consent flow, overwrites the stored credential, and revokes the old token where the vendor allows it. Disconnecting deletes the webhook at the vendor and then deletes the stored secrets.
4. **Least privilege at the vendor.** The documented account for a connection is a dedicated member, invited only to the containers (the boards, spaces, lists or repositories that become Scopes) the routes cover, never an owner or administrator account.
5. **Static configuration keeps working.** A connection configured through environment variables or Helm Secrets is read as today. A store is used only for connections made through the operator API; with no store configured, those calls fail closed instead of falling back to the database or a log.

The ClickUp work in progress on branch `feat/clickup-parity` (webhook lifecycle, status writes, task URLs, dependencies) registers webhooks through the tracker port; this record decides where the secret that registration returns is kept.

### Consequences

* Good, because connecting a tracker or forge, including webhook registration, becomes one consent step with no secret on any clipboard or laptop.
* Good, because the database, its backups, dashboards and every operator consumer hold references only, so a leak of any of them leaks no credential.
* Good, because an installation with OpenBao gets its audit log, versioning and revocation for free, and one without still works.
* Good, because a disconnect leaves nothing behind: no orphan webhook, no forgotten token.
* Bad, because ploegd gains a dependency on a store at run time: a store outage stops new connections and any read that is not cached. Accepted: values are read once and held in memory, as the environment values are today.
* Bad, because Ploeg must hold an OAuth client secret per vendor, configured statically. Accepted: it is one secret per installation and vendor, seeded once, instead of one per connection and webhook.
* Bad, because the chart grows RBAC (a namespaced Role for the Kubernetes adapter) or a vault role, and the code grows a Kubernetes or vault client; neither exists today.
* Neutral, because the residual risk remains that a compromised ploegd pod can read every secret under its own path. It is bounded by the narrow policy, made visible by the store's audit log, and closed by revoking at the vendor and reconnecting.

### Confirmation

Proposed, none of these exist yet:

* A redaction test drives connect, reconnect, webhook registration and disconnect against `httptest` fakes of a vendor and a store, captures every API response body, log line, event payload and database row written, and fails if any contains a stored secret value.
* A `SecretStore` conformance suite, in the style of ADR-0183's tracker suite, runs every adapter (OpenBao or Vault KV against a fake, Kubernetes Secrets against a fake API server) through put, get, overwrite, delete and a path outside its own being refused.
* A test that connecting or registering a webhook through the operator API with no store configured fails closed and writes nothing.
* A test that a connection configured only through environment variables still verifies deliveries and writes back.
* `go test ./internal/ledger/` keeps this record well-formed.

## Pros and Cons of the Options

### Ploeg seals connection secrets in its own database with envelope encryption

* Good, because it adds no run-time dependency: the database is already there.
* Good, because one-click connect works.
* Bad, because the key-encryption key must still live somewhere outside the database, which is a secret store by another name.
* Bad, because the sealed values travel into every backup and every replica, and a database read grant becomes one step from a credential.
* Bad, because Ploeg would own key rotation, audit and revocation, which a vault already does.

### Ploeg only reads secrets a person has put in a vault, by reference

* Good, because Ploeg never writes a secret and needs only read access.
* Bad, because a person still has to put each value there, and the webhook secret a vendor returns once still has to be caught by whoever registered the webhook. One-click connect is impossible.
* Neutral, because it is the static-configuration path this record keeps, with a vault behind it.

## Re-evaluation triggers

* A supported tracker or forge drops the OAuth authorization-code flow, or starts issuing tokens that expire, so Ploeg must refresh them.
* An installation needs a store this record does not name (a cloud provider's secret manager, the External Secrets operator as the only writer).
* A security review finds a stored value in a response, log, event or database row.
* OpenBao changes Kubernetes auth or KV v2 in a way that breaks a path-limited policy.
* A deployment needs one Ploeg to hold connections for several Tenants, so that one path policy is too wide.
