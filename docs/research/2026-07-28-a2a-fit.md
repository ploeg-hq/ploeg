# A2A × Ploeg — protocol-fit dossier

> Surveyed 2026-07-28 via four parallel research agents (spec/docs crawl,
> source-repo dig, ecosystem + absence checks, local seam map) plus a manual
> read of this repo's architecture docs. Condensed verdict lives in
> [design.md §8](../design.md); conditional adoption is backlog item #102.
> This file is the full evidence trail.

**Verdict: adopt nothing now.** A2A is mature and real — but it claims a seam
Ploeg doesn't have: peer communication between *opaque agentic systems across
organizational trust boundaries*. It cannot replace ACP at the harness seam,
cannot replace the lease queue at the executor seam, and inside a single stack
it is overhead by its own community's admission. The one honest fit is a
north-facing facade — "the dark factory as a remote agent" — parked on the
watchlist (backlog #102) with concrete flip triggers.

Unlike the AHP sweep (2026-07-27), the "pre-1.0 + single vendor → dismiss"
heuristic does **not** apply here. A2A fails on fit, not maturity — the
distinction this dossier exists to record.

## 1. What A2A actually is

- **Spec:** v1.0.0 (2026-03-12), v1.0.1 patch (2026-05-28). Normative source
  is `specification/a2a.proto` (proto-first since 1.0; the JSON schema is a
  generated artifact). Version negotiation via a mandatory `A2A-Version`
  header. <https://a2a-protocol.org/latest/specification/>
- **Governance:** Linux Foundation project since 2025-06-23; TSC of eight
  named org seats — Google, Microsoft, AWS, Cisco, Salesforce, ServiceNow,
  SAP, IBM. IBM/BeeAI's competing "Agent Communication Protocol" **merged
  into A2A** 2025-08-29, so that ACP name collision is dead (Zed's Agent
  Client Protocol — our #64 bet — is unrelated and has zero contact with A2A).
- **Wire model:** eleven abstract operations (`SendMessage`,
  `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`,
  `SubscribeToTask`, four push-notification-config methods,
  `GetExtendedAgentCard`) over three interchangeable transports: JSON-RPC 2.0,
  gRPC, REST. No binding is mandated; agents declare transports in their card.
- **Discovery:** JWS-signable **AgentCard** at
  `/.well-known/agent-card.json` — identity, skills, transports, auth schemes
  (OpenAPI-style), extensions.
- **Task lifecycle:** `SUBMITTED → WORKING → {COMPLETED, FAILED, CANCELED,
  REJECTED}` with interrupted states `INPUT_REQUIRED` and `AUTH_REQUIRED`
  (the latter explicitly covers "human approval before a destructive
  action"). Terminal tasks never restart — refinements are new tasks in the
  same `contextId`. Outputs travel as **Artifacts**; messages are explicitly
  not a reliable delivery channel. Async-first: polling, SSE streaming, and
  webhook push notifications for "tasks lasting minutes/hours/days".
- **Self-positioning:** agents collaborate "without needing access to each
  other's internal state, memory, or tools"; *"MCP inside agents, A2A between
  agents"* (<https://a2a-protocol.org/latest/announcing-1.0/>). A protocol
  for addressing a whole agentic system as a black box — not for driving a
  coding harness, which is a session-level, permission-brokered, local-process
  concern (ACP's layer).
- **Go SDK:** official and GA — `github.com/a2aproject/a2a-go/v2` (v2.3.1,
  2026-05-13): server `AgentExecutor`, pluggable `TaskStore`, all three
  transports, auth middleware. Maintained essentially by two Google engineers.
- **Engineering reality:** governance is cross-org but day-to-day commits are
  Google-dominated. Load-bearing open issues: queue/pub-sub transport instead
  of point-to-point RPC (top-reacted,
  <https://github.com/a2aproject/A2A/issues/1029>), confused-deputy
  authorization across delegation chains
  (<https://github.com/a2aproject/A2A/issues/153>), agent registry/discovery
  beyond 1:1 (<https://github.com/a2aproject/A2A/issues/297>).

## 2. Adoption is bimodal — exactly along Ploeg's fault line

**Shipped:** Azure AI Foundry + Copilot Studio, AWS Bedrock AgentCore
(A2A servers sold on the Marketplace), Google ADK / Gemini Enterprise,
LangGraph (every assistant auto-exposes an A2A endpoint), CrewAI, PydanticAI
(`fasta2a`), Dapr Agents (v1.0 GA 2026-03), kagent (CNCF sandbox —
"every kagent agent implements A2A"). Named production users: Tyson Foods,
Gordon Food Service.

**Absent (checked, zero mentions):** OpenHands, Zed's Agent Client Protocol,
Vikunja, Forgejo, KEDA, Anthropic/Claude Code. Even founding TSC member SAP
hasn't GA'd its A2A integration 15 months post-launch (scheduled Q4 2026).

**The decision-relevant finding:** OpenHands — the harness this factory runs
today — closed its community A2A PR unmerged (2025-09), auto-closed the
tracking issue as *not_planned*
(<https://github.com/OpenHands/software-agent-sdk/issues/1060>, maintainer:
"not very sure people are super-interested in A2A anymore"), and shipped
**Zed-style ACP** on its new SDK instead. The strongest external validation
backlog #64 has received.

**Community consensus** (mid-2026 HN threads, "Agents Need a Public Square",
architecture critiques): A2A earns its keep only across organizational trust
boundaries; inside one stack it's chat-shaped overhead — tight availability
coupling, N² point-to-point HTTP, backpressure pushed into every
implementation.

## 3. Layer map

| Seam | Implemented today | A2A's claim |
|---|---|---|
| Board → dispatcher ingest | Vikunja webhook (`pkg/httpapi`) | Could compete — the only seam it plausibly enters, as a *second* front door (see §5) |
| Executor (dispatcher → worker) | Run API ([contracts/executor.md](../contracts/executor.md)) + KEDA | No — point-to-point RPC; A2A's own top issue #1029 begs for the queue semantics our Postgres lease queue already has |
| Worker ↔ coding harness | `harness.Adapter` (`pkg/harness/adapter.go`); ACP bet #64 | No — wrong abstraction (opaque remote peer vs local session); OpenHands rejected A2A and shipped ACP |
| LLM credential/metering | `pkg/llmbroker` → LiteLLM | Orthogonal — but LiteLLM ships a full A2A Agent Gateway (<https://docs.litellm.ai/docs/a2a>): a latent zero-code on/off-ramp already in the deployment |
| Forge / tracker write-back | stubs (`pkg/provider/vikunja`) | No claim — but it's the hard prerequisite for the facade (#31) |
| North-facing run surface | **unclaimed** (AHP parked at #101) | **Yes — the seam A2A actually wants**, and a materially stronger claimant than AHP: 1.0 spec, LF governance, GA Go SDK, real multi-vendor clients |

## 4. The state-machine rhyme

A2A's lifecycle maps onto `pkg/work` nearly 1:1 — which is why a facade would
be cheap, not why it should be built:

| Ploeg | A2A |
|---|---|
| `queued` | `SUBMITTED` |
| `leased` | `WORKING` |
| `needs_human` | `INPUT_REQUIRED` / `AUTH_REQUIRED` |
| `done` | `COMPLETED` |
| `stale` / sweeper `failed` | `FAILED` |
| re-dispatch by re-assignment (VIK-588 review round) | new task in the same `contextId` (terminal tasks never restart) |
| PR URL in `links[]` | `Artifact` |
| unassignment (backlog #8) | `CancelTask` |

## 5. The one honest scenario, and its tension

**Ploegd as an A2A remote agent:** AgentCard skills = teams ("dispatch a
coding task to team silver"), `SendMessage` → work item, `GetTask`/`ListTasks`
→ run state, push notification on outcome, PR link as Artifact. Any
A2A-speaking system — a kagent ops agent, Gemini Enterprise, a future Agora
reviewer agent, another org's factory — could say "fix this" and track the
result without knowing Vikunja exists.

**The named tension:** a second front door beside the Vikunja webhook
violates the design's first commandment — *the tracker and its UIs remain
authoritative* ([design.md](../design.md) §2 non-goals). A work item born via
A2A has no VIK-n ticket: no review-round loop, no re-assignment path, a
broken `Agent-Trace-Id` audit chain. The only architecture-honest shape: the
facade is a **separate service** (never the worker — R6, same rule as the AHP
projector #101) that *creates and assigns a Vikunja ticket* via
TrackerProvider write-backs, then projects state back out. That makes backlog
**#31 (tracker write-backs — stubs today)** the hard prerequisite, exactly as
#64 is the prerequisite for #101.

## 6. Implementation path (only when a §8 trigger fires)

- **Phase 0 — today, zero code:** experiments via LiteLLM's Agent Gateway
  (register/invoke A2A agents at `/a2a/{agent_id}`, OpenAI-compat bridge,
  supports 0.3 + 1.0 wire formats). Kept away from factory credentials; note
  its tracker shows rough edges (bridge pinned to 0.3 wire names, long-running
  task bugs).
- **Phase 1 — read-only projector:** separate `ploeg-a2a` deployment on
  `a2a-go/v2` (`a2asrv` + custom `TaskStore` that *reads* Ploeg state, never
  owns it). Needs one new ploegd read endpoint (`GET /api/v1/items/{id}` —
  only queue snapshots exist today). Serves the AgentCard (skills = team
  roster), `GetTask`/`ListTasks`/`SubscribeToTask` from
  `work_items`+`agent_runs` per the §4 mapping. Auth per A2A §7.4 ("MUST
  authenticate every incoming request") via Authentik OIDC / OpenBao-issued
  credentials.
- **Phase 2 — dispatch:** `SendMessage` → TrackerProvider create+assign
  (#31) → normal webhook path, board stays authoritative; `CancelTask` maps
  to unassignment handling (#8); outcome → push notification + PR-link
  Artifact.
- **Explicitly never:** A2A between factory internals (worker↔harness,
  dispatcher↔worker) — one trust boundary, N² HTTP, no lease/queue
  semantics; and A2A's open confused-deputy gap (#153) is *behind* our
  per-run scoped-credential model, not ahead of it.

## 7. Recommendations

1. **Adopt nothing now.** No component in the dispatch path speaks A2A; the
   would-be clients don't exist in the stack yet.
2. **Keep ACP as the harness seam (#64), with raised confidence** — the
   OpenHands not_planned-A2A / shipped-ACP finding is direct validation.
3. **Ledger entries** — design.md §8 row + backlog #102 (done, this sweep).
4. **Route near-term A2A curiosity through LiteLLM's Agent Gateway**, kept
   away from factory credentials (same posture as the OmniRoute ruling).
5. **Don't reach for A2A for intra-factory team/role delegation (#39/#43).**

## 8. Re-evaluation triggers (any one reopens this)

- A real A2A client lands in the webgrip stack — above all **kagent deployed
  to homelab-cluster** (A2A-native; watch its spec-1.0 migration,
  <https://github.com/kagent-dev/kagent/issues/1941>), or De Vloer / Agora
  wanting programmatic dispatch.
- OpenHands reverses course
  (<https://github.com/OpenHands/software-agent-sdk/issues/1060>).
- A2A grows a queue/pub-sub transport
  (<https://github.com/a2aproject/A2A/issues/1029>) — that would make it a
  genuine executor-seam candidate, not just a facade.
- Vikunja or Forgejo ship any A2A/agent endpoint (both at zero today).
- The 2027-04 review gate turns Ploeg into a product — external adopters
  will want a standard dispatch API, and an A2A facade is the obvious
  product-grade front door.
