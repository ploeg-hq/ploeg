# What the claude-runner orchestrator relies on in Anthropic's on-demand runners

Desk check, 2026-11-18, for [ADR-0197](../adrs/0197-no-credential-enters-a-run-pod-and-a-credential-gateway-outside-it-attaches-each-one-a-run-uses.md) section 7, "The environment secret stays on the orchestrator". Question: does Anthropic's documented on-demand runner interface let the chart keep the environment secret off every pod where a session runs, and start one runner pod per session that holds no Secret?

Verdict: yes, as documented. Nothing here was run against Anthropic's live service; the chart's orchestrator mode rests on the documentation below and on fakes ([test-claude-runner-orchestrator.sh](../../scripts/test-claude-runner-orchestrator.sh)). The live check of section 7's Confirmation still has to pass before an installation relies on it.

Sources, read on 2026-11-18: [Customize sessions, On-demand runners](https://code.claude.com/docs/en/self-hosted-environments-configuration#on-demand-runners), [Self-hosted environments reference, Orchestrator CLI flags](https://code.claude.com/docs/en/self-hosted-environments-reference#orchestrator-cli-flags), [Deploy to production, Harden your deployment](https://code.claude.com/docs/en/self-hosted-environments-deploy#harden-your-deployment) and the [changelog](https://code.claude.com/docs/en/changelog).

## What the documentation says

* **The orchestrator.** `claude self-hosted-runner orchestrator --environment-secret-file <file> --hooks-dir <dir>` polls Anthropic for spawn requests, one per session queued with no runner, and runs `<hooks-dir>/spawn-runner` for each. It keeps no state between polls, so replicas may run side by side; each request is claimed by one replica. "The environment secret stays only on the orchestrator host, which never runs user code; each spawned runner receives a single-use work order that registers exactly one runner and then expires." It accepts `--api-url`, `--environment-secret-file`, `--hooks-dir`, `--health-port` and `--log-level` like the runner, and its own `--hook-concurrency` (4), `--hook-timeout` (60 s), `--expected-spawn-seconds` (120 s, 10 to 3600), `--min-idle` (0), `--shutdown-drain-sec` (0, from 2.1.299) and `--debug-dir`.
* **The hook's input.** `CLAUDE_RUNNER_WORK_ORDER_FILE` (a temp file with the signed work-order JWT, deleted after the hook exits, not to be logged), `CLAUDE_RUNNER_ORDER_ID` (the idempotency key, "safe for Kubernetes resource names"), `CLAUDE_RUNNER_SESSION_ID` and `CLAUDE_RUNNER_SESSION_UUID` (empty for pre-warming), `CLAUDE_RUNNER_ATTEMPT`, `CLAUDE_RUNNER_ORDER_SERVER_TIME`, `CLAUDE_RUNNER_POOL_ID`, `CLAUDE_RUNNER_ACCOUNT_ID`, `CLAUDE_RUNNER_ACCOUNT_EMAIL`, `CLAUDE_RUNNER_PRIMARY_REPO_URL`, `CLAUDE_RUNNER_PRIMARY_REPO_REVISION`, `CLAUDE_RUNNER_REPO_SOURCES`, `CLAUDE_RUNNER_CORRELATION_ID`, `CLAUDE_RUNNER_CLIENT_PLATFORM` (`scheduled_trigger` among its values) and `CLAUDE_RUNNER_SPAWN_REASON` (from 2.1.318).
* **The work order.** The spawned runner registers with it "in place of the environment secret": `--environment-secret-file` pointing at a file with the JWT, or `SELF_HOSTED_RUNNER_ENVIRONMENT_SECRET` set to it. The hook must copy the JWT into the workload, since the file is deleted when it exits. A session-bound order registers one runner bound to that session, so spawned runners use `--capacity 1`. A pre-warming order registers an unbound runner that "claims queued work like a fixed-fleet runner". A restarted on-demand runner cannot register again: "its work order is single-use".
* **The hook contract.** Submit asynchronously and return within `--hook-timeout`; be idempotent on `CLAUDE_RUNNER_ORDER_ID`, never on the session id; never retry the workload; exit 0 for submitted, 1 (or a timeout) for a retryable failure, 2 or higher for one no retry fixes. Anthropic re-requests with a fresh order id when no runner registers within `--expected-spawn-seconds`, and the work order expires with that lease.
* **Idle exit.** A runner exits only when told: `--release-idle-session-min` releases an idle session and exits 0, `--kill-session-after-min` bounds a session. The workload should be removed when the runner exits, for example with `ttlSecondsAfterFinished` on a Kubernetes Job.
* **Hardening.** "Prefer on-demand runners, where the secret stays on the orchestrator host, which never runs user code"; on a fixed fleet "treat the environment-secret file as readable by every session".

## How the chart uses it

* `claudeRunner.mode: orchestrator` runs the orchestrator as a Deployment in the executor namespace. It mounts only the `SELF_HOSTED_RUNNER_ENVIRONMENT_SECRET` key of `claudeRunner.environmentSecret` as a file and passes `--environment-secret-file`, so the secret is not in the environment its hooks inherit. Its ServiceAccount may only create Jobs in that namespace.
* [`spawn-runner`](../../ops/claude-runner/spawn-runner) reads the runner Job the chart renders into a ConfigMap, names it after a hash of the order id (a redelivery meets `409` and succeeds), annotates the session id, adds the work order as `PLOEG_CLAUDE_RUNNER_WORK_ORDER` and creates it through the Kubernetes API. It refuses a request without a session with exit 2, because an unbound standby runner would take any session; the chart never passes `--min-idle`. Kubernetes `400`, `403`, `404` and `422` exit 2, anything else exits 1.
* The runner pod starts [`ploeg-claude-runner-from-work-order`](../../ops/claude-runner/runner-from-work-order), which writes the work order to a memory-backed `emptyDir`, removes it from the environment and starts `claude self-hosted-runner --environment-secret-file <that file>`. The session's processes therefore inherit no work order, and the pod spec names no `SELF_HOSTED_RUNNER_ENVIRONMENT_SECRET`.

## What is accepted, and what stays open

* The work order is a literal value in the runner Job's spec, readable by whoever may read Jobs in the executor namespace until the runner registers. It cannot be put into a Secret, because a runner pod mounts none (ADR-0197 section 4). Anthropic documents it as single-use and session-bound; section 7 accepts it in the runner pod as "spent at registration".
* The wrapper deletes the file once the runner answers `/healthz`, which the reference says it does only after it registered; until then the runner and any session share a user and can read it. Whether Anthropic refuses a second registration with a spent order is documented ("its work order is single-use"), not tested, and the runner pod's safety relies on it (ADR-0197 section 7, item 1).
* A ValidatingAdmissionPolicy scoped to the orchestrator's ServiceAccount admits only the chart's runner Job, because RBAC cannot restrict the pod spec of a Job the hook creates.
* `--expected-spawn-seconds` defaults to 300 in the chart, not 120, because a runner Job installs Claude Code at start (ADR-0141) before it registers.
* `--shutdown-drain-sec` needs Claude Code 2.1.299; the chart pins 2.1.296 and leaves it to `claudeRunner.orchestrator.extraArgs`.
* Not verified: that a session started by a routine with an API trigger is offered to the orchestrator of its self-hosted environment (section 7, item 1), and what `CLAUDE_RUNNER_CLIENT_PLATFORM` and `CLAUDE_RUNNER_ACCOUNT_ID` carry for one.
