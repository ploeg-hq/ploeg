# Managed worker control

The implementation follows [ADR 0025](../adrs/0025-management-authority-stays-in-the-control-plane.md), which remains proposed for human ratification. The existing work payloads remain in the [executor contract](executor.md). Deployment and reconciliation are covered in the [managed-worker operations guide](../ops/managed-workers.md).

## Authority

The controller holds LiteLLM management authority. Worker containers receive a bootstrap capability scoped to one team and role. Successful admission exchanges that capability for a signed capability bound to the Run, worker identity, team, role and worker-control audience. The worker identity travels in `X-Ploeg-Worker-ID`; HTTP authentication uses an Authorization bearer header. Transport must be authenticated and confidential across trust boundaries.

A Run token identifies work; it does not authenticate a managed request. With `PLOEG_TRANSACTION_TOKEN_SIGNING_KEY` set, the claim also answers the Run's transaction token ([ADR-0156](../adrs/0156-each-run-carries-a-transaction-token-that-names-its-person-and-a-team-without-a-sponsor-runs-nothing.md), proposed): an ES256 JWT shaped like an OAuth Transaction Token whose `sub` is the person the Run acts for, `act` the Team and Role acting for them, `txn` the Run's id, `req_wl` the worker id and `exp` the lease deadline. Every renewal answers a fresh one, the worker presents the newest on every Run route, and ploegd publishes its keys at `GET /.well-known/jwks.json`. While ploegd signs them, a Team without `teams.<name>.sponsor` runs nothing: its claims answer 403 with the reason. The HMAC control capability is deprecated: it is still issued and accepted unless `PLOEG_WORKER_HMAC_CAPABILITY=off`, has a maximum lifetime of 24 hours, and carries no person. Each control operation also checks the current Run deadline and state. A finished managed outcome can be delivered again only with its original authenticated capability and identical outcome digest. A changed outcome cannot revise a finished Run.

| Operation | Required authority | Result |
| --- | --- | --- |
| `POST /api/v1/claim` | Bootstrap capability matching the requested team and role; worker identity | Existing claim payload plus `transactionToken` and, unless the HMAC capability is off, `controlToken`; 403 for a Team without a sponsor while ploegd signs transaction tokens; managed inference authorization is reserved first. 426 with the served worker range when `ploegd` does not serve the claim's `workerVersion` ([ADR 0134](../adrs/0134-ploeg-keeps-each-release-compatible-with-the-one-before-and-removes-only-after-a-deprecated-minor.md)) |
| Run renew, checkpoint and outcome routes | Matching transaction token (or deprecated HMAC capability) and worker identity | Existing work-control behavior; a renewal also answers a fresh `transactionToken`. Audit rows written under a transaction token record `detail.runActor` (person, proof, agent, the identity provider's actor, Run) |
| `POST /api/v1/runs/{token}/llm/credential` | Live signed Run capability | One inference key and alias; controller policy selects the budget, models and TTL |
| `POST /api/v1/runs/{token}/llm/block` | Live signed Run capability | Blocks matching gateway keys while retaining accounting identities |
| `GET /api/v1/runs/{token}/llm/spend` | Live signed Run capability | Provisional observed cost; absent gateway accounting is an error |
| `POST /api/v1/runs/{token}/transcript` | Live signed Run capability | Stores a batch of the Run's transcript, clamped and redacted again ([ADR-0090](../adrs/0090-a-runs-agent-session-is-kept-as-a-bounded-redacted-transcript.md)); 404 when ploegd records no transcripts |
| `POST /api/v1/runs/{token}/identity` | Live signed Run capability | One Run identity per audience its declared plugins opted into, signed by ploegd from its own records of the Run and expiring with the lease ([ADR-0149](../adrs/0149-a-declared-plugin-may-receive-a-signed-run-identity-that-names-its-run-and-authorizes-nothing.md)); 404 when ploegd issues none, 409 when the Run is not running. The token authorizes nothing in Ploeg, so the worker writes it into the work directory for the hook guard to read |

A Run the person's own client carries ([ADR-0112](../adrs/0112-a-claude-environment-run-uses-the-claude-login-of-the-person-it-acts-for.md)) is never claimed through `POST /api/v1/claim`: the claim, `PendingRunsFor` and every KEDA query leave out a Run whose `carrier` is `client`. Its person claims it through the operator API, `POST /api/v1/operator/work-items/{id}/claim`, which answers the Run token and, in managed mode, a `transactionToken` and (unless the HMAC capability is off) a `controlToken` signed for the worker identity `client:<person>`, with the same scope and lifetimes as a worker's. The client then uses the Run routes above with it: `claude-session` to record the session it dispatched, renew and outcome. Once the session is recorded, ploegd holds the Run and its Lease until `PLOEG_CLAUDE_SESSION_TIMEOUT` (default 100m) and settles the Run from the runner's `POST /api/v1/claude-sessions/report`, authenticated by the session token, so the client may leave. A client that stays may still renew, which never shortens that deadline, and report the outcome, which finishes the Run first. A report for a session no running Run recorded answers 404, and a Run whose runner never reports ends at its deadline as any lapsed Run does. No inference authorization is reserved and no inference key is minted for such a Run, because the person's own Claude seat pays for it.

Managed worker queue snapshots are unavailable. `GET /api/v1/queue/depth` was removed on 2026-09-23 because nothing consumed it. Human applications use the separately authorized [operator contract](README.md#operator-read-consumers).

Operator execution credential issuance uses the same account but also checks its exact execution generation, live deadline and running state under the execution lock. The checks occur before the external mint and again before recording the returned credential. A pause or generation change during mint prevents credential delivery; cleanup attempts to block the returned key and retains the unresolved hold.

## Accounting states

The account is independent of the worker outcome and lives in [migration 0012](../../pkg/store/migrations/0012_run_llm_accounts.sql). The controller records account mutations and audit events atomically. The following states are implemented in [the account store](../../pkg/store/llm_accounts.go):

| State | Meaning | Budget treatment |
| --- | --- | --- |
| `reserved` | Admission exists; no mint has begun | Authorization remains held |
| `minting` | Durable external-mint intent has been claimed | Authorization remains held; another request cannot mint |
| `issued` | Gateway identity was recorded after a successful mint | Hold is at least the authorization or higher observed cost |
| `unknown` | An external effect or response cannot be established | Hold remains; no automatic replacement credential |
| `blocked` | Gateway blocking was confirmed, the gateway reported that it holds no key for the account, or an untouched reservation was atomically prevented from minting | Hold remains because observed spend is provisional |
| `reconciled` | A trusted caller supplied final evidence for a finished Run | Reconciled cost is charged to its Shift; any subsequently observed positive delta remains held |

Mint intent has one durable winner. If a response is lost, retry does not mint another key or reconstruct the plaintext credential. A controller restart cannot turn an unknown mint into a new paid attempt.

Managed worker outcomes do not settle the account. Worker failure, lease expiry, repeated zero gateway observations and successful key blocking do not prove final zero cost. `ReconcileLLMAccount` requires a finished Run, trusted evidence and a nonnegative amount no lower than recorded observations or previous reconciliation. An unchanged reconciliation adds no duplicate spend; a later positive correction charges only its delta. An untouched reserved account may be reconciled as zero with evidence that mint never began. Blocking an untouched reservation records a zero observation and prevents any later mint; it retains the hold until trusted reconciliation. Repeated blocking is idempotent. The controller's settlement sweep is the trusted caller: it settles never-minted accounts at zero and blocked accounts at the gateway's spend-log total after a quiet period, as described in [the managed-worker runbook](../ops/managed-workers.md#reconcile-uncertainty).

## Workspace boundary

Workers cannot instantiate a LiteLLM administrative broker. Startup rejects known administrative environment variables as an additional configuration check. The deployment boundary is the controller-only Secret wiring in [the Helm chart](../../ops/helm/ploeg/templates/_worker_control.tpl); a name denylist alone is not isolation.

Harness child environments are built from a small allowlist and a dedicated HOME, temporary directory and XDG paths. They receive the assigned inference key and, for a writer, its selected forge capability. OpenCode configuration stores an environment reference to `LLM_API_KEY`. The `qwen-code` and `goose` ACP profiles receive the key only as environment variables ([ACP profiles](acp-profiles.md)). Git authentication uses transient environment configuration scoped to the exact repository URL; clone URLs and `.git/config` do not contain the credential. The harness runs in its own container of the Run's pod ([ADR-0138](../adrs/0138-a-harness-runs-in-its-own-container-and-no-credential-enters-it.md), chart `executor.harnessContainer: separate`). The worker listens on `PLOEG_HARNESS_LAUNCHER`, a Unix socket in a volume both containers mount, accepts exactly one connection from `ploeg-worker harness-serve`, the first process of the harness container, and removes the socket. Every process of the Run that needs the harness image (the harness, the verification commands, the OpenSpec CLI, the version and binary probes) is started over that connection with the environment the worker prepared; stdio, exit status and signals to the process group come back the same way ([pkg/harness/launch](../../pkg/harness/launch/)). The worker refuses a launcher that is not process 1 of its own PID namespace, because a pod with `shareProcessNamespace` would make the worker's processes visible to the harness. The harness container mounts no Secret and has no environment of its own, so the bootstrap token, the builder forge token, the per-Run key and the per-Run forge token, and the worker's credentialed `git` children, are in another container with its own PID namespace and root filesystem. After the harness exits the worker has the launcher end every process left in the harness container, including one that left the harness's process group, before the OpenSpec gate and verification run. As a second layer the worker marks its own process non-dumpable ([conceal_linux.go](../../pkg/worker/conceal_linux.go)); that flag covers the worker process only, because `execve` makes every child dumpable again, which is why a workload with `harnessContainer: shared` exposes the token in the environment of the worker's `git` children to a same-user harness. With `PLOEG_LLM_KEY_ISOLATION=proxy` (chart value `executor.litellm.keyIsolation`) the worker does not hand over the per-Run model key either: the harness receives a random placeholder and a loopback base URL, and a reverse proxy inside the worker ([llmproxy.go](../../pkg/worker/llmproxy.go)) replaces the placeholder with the real key on each request to LiteLLM, streaming unchanged. The proxy stops when the Run ends. A harness that calls the model from inside a DinD container cannot reach the worker's loopback, so the chart sets both proxies by default only for a qualified harness without DinD and passes the reason it left them off in `PLOEG_CREDENTIAL_ISOLATION_OFF_REASON`, which the worker logs at boot ([qualification record](../research/2026-10-04-isolation-qualification.md)). `PLOEG_FORGE_TOKEN_ISOLATION=proxy` (chart value `executor.forgeTokenIsolation`) does the same for a writer's forge token ([forgeproxy.go](../../pkg/worker/forgeproxy.go)): git is redirected to a loopback proxy with `url.<proxy>/.insteadOf`, the prompt names the proxy as the forge URL, and `AGENT_BUILDER_TOKEN` holds a placeholder. The proxy decodes each path segment first and answers 403 to any dot segment, encoded separator (`%2f`, `%5c`) or double encoding; the one exception is GitLab's project ID, which must equal the Run's encoded project path exactly. On GitHub the API lives under `/api/v3/repos/<owner>/<repo>` on the proxy; for github.com the proxy forwards it to `api.github.com` without the prefix, sends the token as `Authorization: Bearer`, and authenticates git as `x-access-token`. A GitHub token that expires (an App installation token, ADR-0086) is refreshed by the worker through `POST /api/v1/runs/{token}/forge-credential` before it does, and the proxy always sends the current one. It then adds the real token only for the Role's allowlist in the Run's own repository: smart-HTTP git fetch and push, reading and opening or updating the pull or merge request, reading and posting issue and pull request comments, and reading commit statuses (and, on GitHub, check runs). A reader's allowlist drops push and opening or updating the request; the worker starts the proxy for writers only. A push is fenced to the Run's branch: before forwarding `git-receive-pack`, the proxy reads the pkt-line command list up to its flush-pkt (inflating a gzip body; any other content encoding gets 403) and answers 403 unless every ref update targets `refs/heads/<run branch>` and none deletes it. Tags, other branches, a push certificate and an unparseable command list get 403. An empty command list, the probe git sends before a large push, passes. The inspected bytes are replayed ahead of the rest of the stream, so the forge receives the push unchanged. A writing Run also gets a per-Run canary: `GITHUB_PAT` holds a random value shaped like a GitHub personal access token that no forge accepts. The worker watches the Run's real model key, its real forge token and the canary ([leakwatch.go](../../pkg/worker/leakwatch.go)). The forge proxy answers 403 to any API request whose body or query carries one of them. It logs one ERROR naming the Run's trace, the Work Item, the credential kind and the route, never the value, and from then on refuses every forge write of the Run. Reads still pass. Before the Run is reported, the worker fetches the Run's branch from the forge and scans `git log --patch` of the commits this Run pushed, messages and authors included. A hit ends the Run `failed` with failure reason `credential_leak`, no links and no verdict. The pushed commits stay on the branch for forensics. ploegd never retries such a Run: it parks the Work Item at `needs_human` and closes the branch's open pull request ([ADR-0105](../adrs/0105-a-credential-leak-parks-the-work-item-and-closes-its-pull-request.md)). If the scan cannot run, a Run that claims delivery becomes `stuck` instead. The Run's proposed learnings are checked for the same values before the worker keeps them for review; a hit fails the Run the same way, and a Run that leaked anywhere keeps no learnings. Every git command the worker itself runs once the harness has had the clone (the unpublished-work check, the leak scan's fetch and log, the OpenSpec gate and the verification's commit and status reads) runs in a git directory the worker creates after the harness exits ([workergit.go](../../pkg/worker/workergit.go)). That directory borrows the clone's objects through `objects/info/alternates`, copies the clone's `HEAD`, branch and remote-tracking refs and shallow list from their files, and names the forge URL explicitly, with no system or global configuration. Git never reads the clone's `.git/config` or hooks, so a `url.*.insteadOf`, `http.extraHeader`, `core.hooksPath`, `core.fsmonitor`, `include.path` or credential helper the harness writes there cannot redirect, observe or run inside the worker's credentialed git. The OpenSpec gate validates an export of the pushed branch in that directory instead of checking it out over the harness's working tree. While the harness runs, the worker's only credentialed git is the board watch's `git ls-remote` of the Run's branch; it names the forge URL explicitly and runs in a fresh empty directory outside any repository, with `GIT_CEILING_DIRECTORIES` set to that directory ([git.go](../../pkg/worker/git.go), `runGitOutsideAnyRepository`), so the clone's `.git/config` is never read while the token is in play. The post-Run read that confirms a verified branch head did not move runs the same way. The watch's local `git cat-file` in the clone carries no token. Model gateway traffic is not scanned: prompts legitimately carry tool output, including environment listings, and the gateway is the Run's own metered egress, not a place where a value outlives the Run. Both proxies forward only requests that present the Run's placeholder, compared in constant time, and answer 403 to anything else, so another process on the pod's loopback cannot borrow the credential. The model proxy reads it from `Authorization: Bearer` or `X-Api-Key`; the observer the worker starts without isolation has no key to protect and checks nothing. The forge proxy reads it from a Basic password, a `token` or `Bearer` authorization or `PRIVATE-TOKEN`, and the git `insteadOf` URL carries it as the Basic password of `agent-builder`. A git request with no credential at all gets a `401` Basic challenge instead of a 403, because git sends URL credentials only after the server asks. Merging, deleting, settings, collaborators or members, hooks, branch protection, keys, other repositories, user and admin endpoints all get 403.

With the harness in its own container the worker and the harness share the pod's network namespace and the work directory, and nothing else: loopback listeners are common to both, which the proxies answer with 403 without the Run's placeholder, and the work directory holds no credential. A workload with DinD, a credential proxy off, `claude-environment` or the deprecated `harnessContainer: shared` keeps the harness in the worker's container, where a workspace may inspect same-identity resources such as `/proc` and discover its scope-limited bootstrap or forge capability. The controller's management, signing and operator credentials must remain absent from every worker pod either way. This foundation does not establish repository write fencing or cluster egress policy.

## Compatibility

Managed mode is the default and fails closed when identity, policy or broker configuration is missing. Legacy operation requires the controller's explicit `legacy` worker-auth mode and the worker's `static-compatibility` credential mode. Legacy mode cannot simultaneously carry the managed signing key or bootstrap registry. Existing unmanaged rows preserve their previous accounting interpretation; they are not upgraded into evidence of managed settlement.

No automatic downgrade, live deployment or migration of existing external credentials is performed by this change.
