# Tracker execution binding

This additive contract implements [ADR 0026](../adrs/0026-tracker-selections-bind-the-canonical-work-item.md) alongside the [operator read API](operator-api.v1.schema.json) and [operator execution authority](../adrs/0024-operator-work-uses-one-execution-authority.md). Its wire shape is checked against [the v1 schema](tracker-execution.v1.schema.json).

`GET /api/v1/operator/work-items/lookup` requires a named consumer bearer and exactly one `provider`, `externalId`, `scope` and `baseUrl` query parameter. It returns `schemaVersion: "1.0"`, the existing operator `item` projection, and the complete `source` expectation object. This read needs no actor header. An unknown item or an item outside consumer team scope returns 404. Unresolved targets, non-pristine work, unavailable provider reads, changed identity or non-open tasks return 409. Malformed or duplicate parameters return 400. Responses never contain credentials.

The source identifies one configured singleton provider by its key and normalized API root, one native task ID and Scope. Vikunja uses its configured `/api/v1` root, task project, `updated` revision and an explicit false `done` value. ClickUp uses its configured `/api/v2` root, task list, `date_updated` revision and an unarchived `open` or `custom` status type. Missing or unknown status does not authorize execution. Another instance of the same provider kind is unsupported by the current Work Item identity; its API root must not be silently substituted. A supplied root is an equality check, never a caller-selected outbound destination.

The workbench passes the returned `source` as an optional field in `POST /api/v1/operator/executions`, with the usual server-authenticated actor header and execution scope. It also checks its independently configured repository target and freshly fetched task. Its content snapshot hash is separate from the provider-native revision. Ploeg re-reads the configured tracker and compares native revision, Scope and explicit open state. Both lookup and new admission require a current configured target rule whose exact result matches the stored target; a configured container Team pin must also agree. Missing routing or a rule changed since the last webhook fails closed. The declared Forge must be registered; its repository URL and base branch must exactly match the requested execution repository. Native revision alone does not authorize a repository change.

The database then locks the existing Work Item and compares `workItemId`, `provider`, `externalId`, `expectedScope`, `expectedRevision`, `expectedUpdatedAt`, `expectedTarget` and the authorized Team. Only queued assignment work with no previous execution, checkpoints, leases, spend or accounting is eligible. An entirely unstarted pending Shift roster may be retired. Conflicting claim locks produce 409 without waiting in a reversed lock order. The adoption transaction records source provenance, retains tracker origin and identity, sets the durable operator ownership fence, and creates one new operator Shift, Run and Lease on that same Work Item.

The session idempotency key and complete source fingerprint protect accepted admission replay. An identical lost-response retry returns the accepted execution even if the tracker has since changed. A different actor, source or execution request cannot reuse it. Freshness checks happen before the local transaction; a tracker edit can race that transaction because the tracker does not participate in a distributed lock.

Operator ownership survives pause, cancellation, expiry and completion. Tracker updates can refresh mirrored content but cannot change the bound Team or Work Target, requeue the item, or let the unattended scheduler claim, reopen, settle or expire its operator Run. No automatic relinquishment is implemented. Existing started or historical unattended work requires a later explicit transfer protocol. Completion does not imply publication or silently update tracker status.
